# AI 编程工作流 Skill — 通用任务处理框架

> **适用场景**：所有需要 AI 辅助的编程任务，包括功能开发、Bug 修复、优化、重构、合并、安全治理等。
> **核心思想**：不依赖假设，通过"诊断→调研→设计→对抗→验证→拆分→执行"的闭环，确保代码变更的正确性和安全性。
> **最后更新**：2026-05-22

---

## 工作流总览（8 阶段）

```
P0 现状诊断 ──→ P1 需求澄清 ──→ P2 深度调研 ──→ P3 初版方案
    ↑                                              ↓
P7 最终验证 ←── P6 子任务拆分 ←── P5 红蓝对抗 ←── P4 交叉验证
    ↓
P8 并行执行（子 agent 派发）
```

---

## 工作流 8 阶段详解

### P0: 现状诊断（Context Gathering）

**目标**：建立对项目当前状态的完整认知，识别"为什么现在必须做这件事"。

**动作清单**：

| 任务类型 | 动作 | Bug 修复 | 功能开发 | 重构 | 安全治理 | 合并 |
|---|---|:---:|:---:|:---:|:---:|:---:|
| Git 扫描 | `git status` / `log` / `diff` | ✅ | ✅ | ✅ | ✅ | ✅ |
| 文档读取 | README / 审计报告 / 设计文档 | 可选 | ✅ | ✅ | ✅ | ✅ |
| 工作区检查 | 未跟踪文件 / `.gitignore` | ✅ | ✅ | ✅ | ✅ | ✅ |
| 错误定位 | 复现步骤 / 错误日志 / 堆栈 | ✅ | — | — | — | — |
| 需求理解 | 用户描述 / 验收标准 | — | ✅ | ✅ | ✅ | — |
| 冲突检查 | 与主干差异 / 合并冲突预览 | — | — | — | — | ✅ |

**输出**：
- 当前状态快照（分支、提交、改动规模）
- 已知问题清单（Bug 报告、审计问题、TODO）
- 工作区残留项

**检查点**：
- [ ] 当前分支名和最后提交日期已确认
- [ ] 与默认分支的差异已量化（合并任务时）
- [ ] Bug 的复现步骤和错误日志已获取（Bug 修复时）
- [ ] 工作区残留项已识别

**常见陷阱**：
- ⚠️ 忽略 `git status` 中的未跟踪文件
- ⚠️ Bug 修复时不获取完整的错误堆栈
- ⚠️ 合并任务时不预览冲突范围

---

### P1: 需求澄清（Constraint Extraction）

**目标**：从用户的自然语言描述中提取**明确的约束**和**优先级**。

**动作清单**：

1. **追问关键决策**
   - "这个功能需要兼容旧数据吗？"
   - "合并前做还是合并后做？"
   - "紧急程度？是否可以分阶段交付？"
   - "哪些文件/逻辑绝对不能改？"

2. **识别隐含约束**
   - 用户说"优化性能"→ 需要基准测试数据
   - 用户说"数据库统一管理"→ 需要 Admin API + RBAC
   - 用户说"先留个口子"→ 预留接口但暂不实现

3. **确认验收标准**
   - Bug 修复："修复后如何验证？"
   - 功能开发："验收条件是什么？"
   - 重构："行为不变性如何保证？"

**输出**：
- 明确的需求列表（Must / Should / Could）
- 技术约束清单
- 验收标准
- 风险接受声明

**检查点**：
- [ ] 用户已确认"Must"需求
- [ ] 已明确"不做"的边界
- [ ] 验收标准可验证、可量化

**常见陷阱**：
- ⚠️ 假设用户已看过相关文档
- ⚠️ 遗漏"不合并"等关键决策
- ⚠️ 验收标准模糊（如"更快"而非"P95 < 100ms"）

---

### P2: 深度调研（Deep Dive）

**目标**：对代码现状进行精确到文件/行号的调研，**不依赖假设**。

**动作清单**：

| 调研类型 | 方法 | 适用场景 |
|---|---|---|
| 错误追踪 | 从报错堆栈定位到具体文件/行号 | Bug 修复 |
| 代码阅读 | `read_file` 读取相关文件完整内容 | 所有任务 |
| 跨文件搜索 | `grep_search` 查找引用、import、调用链 | 重构、删除代码 |
| 子 agent 调研 | `runSubagent(Explore)` 并行调研多个模块 | 大型重构、架构变更 |
| 依赖分析 | 梳理 import 链、调用关系 | 删除模块、修改公共接口 |
| 数据流分析 | 追踪数据从输入到输出的完整路径 | Bug 修复、性能优化 |

**输出**：
- 精确的文件-行号映射表
- 依赖关系图（import 链、调用图）
- "现状 vs 假设"偏差清单

**检查点**：
- [ ] 每个关键文件已读（或子 agent 已返回摘要）
- [ ] 跨文件引用已扫描（`grep_search`）
- [ ] 依赖关系已梳理

**常见陷阱**：
- ⚠️ 只读文档不读代码，导致方案与现状脱节
- ⚠️ 忽略辅助模块的跨文件引用
- ⚠️ Bug 修复时只改报错位置，不追踪根本原因

---

### P3: 初版方案（First Draft）

**目标**：基于调研结果，输出一份覆盖所有需求的技术方案。

**方案模板**：

```markdown
## 问题描述
[一句话概括]

## 根因分析（Bug 修复时）
[数据流 / 调用链 / 状态变化分析]

## 设计方案
### 选项 A：[简述]
- 优点：
- 缺点：
- 风险：

### 选项 B：[简述]
- 优点：
- 缺点：
- 风险：

## 推荐方案
[选定选项 + 理由]

## 代码级变更
### 文件 1: [路径]
**变更**：[描述]
```python
# BEFORE:
[代码]
# AFTER:
[代码]
```

## 优先级
- P0：[必须完成]
- P1：[建议完成]
- P2：[排期完成]

## 预估工时
[X 小时 / 天]
```

**输出**：
- 完整方案文档（含代码片段）
- 任务清单（P0/P1/P2）
- 预估工时

**检查点**：
- [ ] 方案覆盖所有 Must 需求
- [ ] 有代码级细节（不是纯描述）
- [ ] 工时预估已给出

**常见陷阱**：
- ⚠️ 方案过于抽象，没有代码级细节
- ⚠️ Bug 修复只治标（改报错处），不治本（改根因）
- ⚠️ 未考虑对现有测试的影响

---

### P4: 交叉验证（Cross-Validation）

**目标**：用**代码静态分析**验证方案中的每个断言是否成立。

**验证清单**：

| 验证项 | 方法 | 示例 |
|---|---|---|
| 现状描述是否准确 | `read_file` / `grep_search` | 方案说"用 useEffect"→ 实际代码已改 TanStack Query |
| 方案可行性 | 验证技术约束 | 方案说"加 CHECK 约束"→ 验证当前是否有 CHECK |
| 依赖冲突 | `grep "import xxx"` | 要删除的文件被哪些地方引用 |
| 兼容性 | 检查调用方 | 修改函数签名后，所有调用方是否同步更新 |
| 测试覆盖 | 检查现有测试 | 改动是否破坏现有测试 |

**输出**：
- "方案描述 vs 实际代码"偏差表
- 依赖冲突清单
- 方案修正建议

**检查点**：
- [ ] 方案中的每个"现状描述"已用代码验证
- [ ] 依赖冲突已识别
- [ ] 测试影响已评估

**常见陷阱**：
- ⚠️ 交叉验证流于形式，未发现关键偏差
- ⚠️ 忽略"文档/报告已过时"的情况

---

### P5: 红蓝对抗（Red-Team Review）

**目标**：以**攻击者视角**逐条反驳方案，发现漏洞和缺陷。

**攻击维度**：

| 维度 | 攻击角度 | 适用场景 |
|---|---|---|
| 安全攻击 | "这个设计有什么安全漏洞？" | 所有涉及鉴权、数据、配置的变更 |
| 工程攻击 | "这个改动会破坏什么？" | 重构、删除代码、修改公共接口 |
| 性能攻击 | "这个方案在高负载下会怎样？" | 优化、新增查询、循环处理 |
| 兼容性攻击 | "旧数据/旧客户端会受影响吗？" | 数据模型变更、API 变更 |
| 运维攻击 | "生产环境部署会失败吗？" | 配置变更、依赖升级、迁移脚本 |
| 用户体验攻击 | "这个改动会让用户困惑吗？" | UI 变更、交互变更、错误提示 |

**输出**：
- 每轮对抗的"反驳点 + 修正方案"表
- 加固项清单
- 风险回退方案

**检查点**：
- [ ] 每个设计决策已至少被反驳一次
- [ ] 所有 P0 问题已确认无法被绕过
- [ ] 风险回退方案已准备

**常见陷阱**：
- ⚠️ 红队攻击不够深入，只停留在表面
- ⚠️ 发现冲突后未给出具体修正方案

---

### P6: 子任务拆分（Task Decomposition）

**目标**：将方案拆分为**影响域严格隔离**的子任务。

**拆分原则**：

| 原则 | 说明 | 反例 |
|---|---|---|
| 文件级隔离 | 并行任务不修改同一文件 | "改 9 个 API 文件"作为一个任务 |
| 依赖单向 | Wave N 只依赖 Wave N-1 | Wave 2 的任务依赖 Wave 3 的输出 |
| 验收可独立 | 每个任务有独立验收标准 | "所有测试通过"作为单个验收标准 |
| 工时可控 | 单个任务不超过 1 天 | 一个任务预估 5 天 |
| 粒度适中 | 足够细以并行，足够粗以有意义 | 每个函数一个任务 |

**Wave 分组规则**：

```
Wave 1：零依赖任务（基础设施、独立模块）
Wave 2：依赖 Wave 1 输出的任务（使用新接口、新工具）
Wave 3：依赖 Wave 2 的任务（集成、端到端）
...
```

**输出**：
- 子任务清单（编号、影响域、变更点、验收标准、工时）
- Wave 执行图
- 依赖冲突解决记录

**检查点**：
- [ ] 每个 Wave 内任务无共享文件
- [ ] 跨 Wave 依赖单向无循环
- [ ] 每个任务有明确验收标准

**常见陷阱**：
- ⚠️ 忽略 import 链的隐式依赖
- ⚠️ 任务粒度太粗导致无法并行
- ⚠️ 未预留回归测试任务

---

### P7: 最终验证（Final Review）

**目标**：执行前最后一次确认方案的完整性和可行性。

**验证清单**：

| 检查项 | 内容 |
|---|---|
| 完整性 | 所有 Must 需求已分配任务；P0 问题已覆盖；前后端/DB 已对齐 |
| 可行性 | 工时合理；无单点瓶颈；风险任务有回退方案 |
| 验收标准 | 每个任务标准明确可验证；回归测试触发条件已定义 |
| 用户确认 | 用户已确认"没有问题" |

**输出**：
- 最终方案文档（v-final）
- 验收检查清单
- 风险声明和回退方案

**检查点**：
- [ ] 用户已确认最终方案
- [ ] 所有子任务已编号
- [ ] 总工期已确认

**常见陷阱**：
- ⚠️ 急于执行，跳过最终验证
- ⚠️ 验收标准模糊

---

### P8: 并行执行（Parallel Execution）

**目标**：按 Wave 分组，同时派发子 agent 执行。

**执行规则**：

1. **Wave 内并行**：同一 Wave 所有任务同时启动
2. **Wave 间串行**：Wave N 等 Wave N-1 全部完成
3. **验收 Gate**：每个任务完成后必须验收通过
4. **冲突处理**：发现未预料冲突，回退到 P6 重新拆分

**子 agent 指令模板**：

```
你是 [角色]，负责执行子任务 [T编号]。

## 背景
[当前 Wave 的上下文，前置任务已完成的内容]

## 影响域
[文件列表，绝对路径]

## 变更点
[具体描述，精确到函数/类/行]

## 验收标准
[可验证的条件，如"pytest test_xxx.py 通过"]

## 禁止
[不能做的事，如"不要修改其他文件"]

## 关键代码上下文
```python
[当前代码片段]
```

## 参考
[相关文件路径、设计文档链接]
```

**输出**：
- 每个子任务的代码变更
- 验收结果（通过/失败）
- 回归测试报告

**检查点**：
- [ ] Wave N-1 全部验收通过
- [ ] 子 agent 指令包含完整上下文
- [ ] 每个变更有 commit 记录

**常见陷阱**：
- ⚠️ 子 agent 缺少上下文导致改错文件
- ⚠️ Wave 内任务实际有隐藏依赖

## 附录 A：任务类型速查表

| 任务类型 | P0 重点 | P2 重点 | P3 重点 | P5 重点 | P6 拆分策略 |
|---|---|---|---|---|---|
| **Bug 修复** | 复现步骤、错误日志 | 根因追踪、数据流分析 | 最小改动修复 | "修复是否彻底？""是否引入新 Bug？" | 单文件修复即可并行 |
| **功能开发** | 需求文档、验收标准 | 现有架构、扩展点 | API 设计、数据模型 | "兼容性？性能？安全？" | 按层拆分（DB→API→前端） |
| **重构** | 重构范围、动机 | 全量引用、调用链 | 行为不变性保证 | "会破坏什么？回退方案？" | 按模块拆分，保留兼容层 |
| **性能优化** | 基准测试、瓶颈点 | 热点代码、查询分析 | 优化方案对比 | "高负载下会怎样？" | 按优化点拆分 |
| **安全治理** | 审计报告、漏洞清单 | RBAC/加密/数据流 | 加固方案 | 多轮深度攻击 | 按安全域拆分 |
| **合并** | 冲突预览、分支差异 | 冲突文件内容 | 合并策略 | "合并后会破坏什么？" | 按冲突文件拆分 |

## 附录 D：关键教训（来自实战）

1. **代码 > 文档**：审计报告说"错误"，代码注释说明是"有意设计"。**永远以代码为准**。
2. **安全设计要经得起攻击**：初版想加 role 到 JWT，红队发现 24h 过期窗口。
3. **拆分前必须扫 import 链**：辅助模块被 8 个文件引用，差点导致编译失败。
4. **职责分离**：种子脚本不是数据库，真实数据应通过 API 录入。
5. **粗粒度估算会低估**：复杂 SQL 重写需理解业务语义，必须单独拆分。
6. **Bug 修复要治根因**：不是改报错处，而是追踪数据流到源头。
7. **验收标准要量化**：不是"测试通过"，而是"pytest 23/23 通过"。
8. **用户确认是 Gate**：每个关键阶段必须得到用户"没有问题"的确认。
9. **执行后必须二次红蓝验证**：修改完成后用 `get_errors` + `grep_search` 重新扫描漏洞，不是改完就结束。
10. **子 agent 编辑文件有局限**：VS Code 环境下子 agent 可能无法直接修改文件，应改为"子 agent 调研 → 主 agent 串行编辑"。
11. **Alembic down_revision 必须验证 head**：创建迁移前用 `list_dir` 查看最新版本号，避免 revision 链断裂。
12. **虚构数据要有明显标识**：种子数据中的敏感值应使用 99.99、999.99、"demo-xxx" 等一眼可辨的占位符。
13. **同步更新忽略文件和说明文件**：新增目录/敏感数据时，必须同时更新 `.gitignore` + 添加 `README.md` 说明用途，否则新开发者会困惑。
14. **验证后必须提交远程作为存档**：每个 Wave 结束后应 `git commit && git push`，便于会议汇报进度和出错回退。
