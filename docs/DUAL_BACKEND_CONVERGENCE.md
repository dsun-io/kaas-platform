## 1. 为什么不能简单"让线上跑同一份代码"

这是必须先说清的前提，否则方案会被误导到"直接复用 orchestrator"：

| 约束 | 证据 | 后果 |
|---|---|---|
| **Pyodide 不支持 C 扩展** | `worker/pyproject.toml` 依赖仅 6 个包；orchestrator 有 `psycopg2`/`bcrypt`(C)/`oss2`/`minio`/`openpyxl` | 这些包**进不了** Worker |
| **启动 CPU 限额** | `DEPLOY.md §0.2`：冷启动 ~2.8s，超限会让 isolate 启动失败 → 间歇 5xx；`ecf50ad` 专门修过 | 依赖越多越危险，**不能"把 orchestrator 全塞进去"** |
| **SQLAlchemy + alembic 不可用** | Worker 是裸 asyncpg + 手写 SQL | 数据访问层天然无法整体复用 |

> 结论：**要么换运行时，要么分层**。本方案的默认路径是**分层 + 门禁**，
> 把"换运行时"作为中期评估项（§7），不阻塞当前交付。


## 3. 第 1 步：共享内核 `backend/common/`

### 3.1 技术前提（**W0 必须先验证**）

Worker 能否 import 仓库内的共享包，是整个方案的地基：

| 路径 | 做法 | 风险 |
|---|---|---|
| **Plan A（首选）** | `backend/worker/pyproject.toml` 加 uv 本地路径依赖（`tool.uv.sources` 指向 `../common`），`pywrangler deploy` 打包时一并带入 | 需验证 Pyodide 打包器对本地路径依赖的支持（**未知**） |
| **Plan B（保底）** | 构建脚本把 `backend/common/**` **自动复制**到 `backend/worker/src/_common/`，并由 CI 校验"复制产物 == 源" | 引入"生成产物"，但**复制是自动的**（区别于现在的手工抄写），且 CI 卡住不一致 |

> 验证方法：W0 先写一个最小 `common/version.py`（返回常量），在 worker 里 import 并在
> `/health` 里回显，deploy 到预发验证。**这一步不通过就退 Plan B**，不猜。

### 3.2 内核放什么 / 不放什么

| ✅ 放进来（纯逻辑，可单测） | ❌ 不放（必须有 I/O 或重依赖） |
|---|---|
| 单证/订单**状态机**（合法迁移表） | 数据库连接、SQLAlchemy Session |
| **取号规则**（`doc_sequences` 的号段算法） | HTTP 客户端、对象存储 SDK |
| **上游快照组装**（输入上游 dict → 输出 `raw_payload.sources`） | 邮件/短信发送 |
| **金额/汇率/退税**计算 | 文件读写、模板文件加载 |
| **条款校验**（Incoterms、单据必填项） | 调度器、缓存 |
| **SQL 常量**（见 3.3）+ 参数适配器 | ORM 模型定义（两侧各自维护） |
| 响应结构 schema（pydantic） | — |

**判定准则**：如果一个函数需要"连网/连库/读文件"才能跑，它就不属于内核。
这样内核天然可测（纯函数，两侧同一份单测）。

### 3.3 数据访问层怎么共享（关键设计）

数据访问层无法整体复用（SQLAlchemy vs asyncpg），但**SQL 语句本身可以只有一份**：

```python
# backend/common/queries/trade_docs.py
SELECT_DOC       = "SELECT * FROM trade_docs WHERE tenant_id = :tenant_id AND id = :doc_id"
SELECT_ITEMS     = ("SELECT * FROM trade_doc_items WHERE tenant_id = :tenant_id"
                    " AND trade_doc_id = :doc_id ORDER BY sort_order, id")
INSERT_DOC       = ("INSERT INTO trade_docs (tenant_id, doc_no, doc_type, ...)"
                    " VALUES (:tenant_id, :doc_no, :doc_type, ...) RETURNING id")
```

- **orchestrator**：`await db.execute(text(SELECT_DOC), {...})` —— SQLAlchemy `text()` 原生支持 `:name`
- **worker**：`common.sql.bind(sql, params)` 把 `:name` 机械转换为 `$1…$n` 并按序取参，再交给 asyncpg
  （这是**纯函数，可完整单测**：断言占位符数量 == 参数数量、顺序正确、缺参报错）

这样 SQL 只有一份，且**两侧占位符语义一致**，天然消灭"WHERE 条件被改歪了"这类漂移。

> 注意：`bind()` 必须正确处理**同一参数出现多次**（`:tenant_id` 出现两次 → 复用 `$1`，不能重复占位）。

## 4. 第 2 步：单证工位作为新模式样板

W1 的全部后端改动都按新模式落地：

| 改动 | 内核（写一遍） | orchestrator（薄适配） | worker（薄适配） |
|---|---|---|---|
| 企业主体信息 | 校验 + 默认值填充 + 渲染数据组装 | GET/PUT 的 SQL 执行 | 同 |
| 快照补 `spec_snapshot` / 买方详情 | `build_order_snapshot(row, items, customer)` | 查库 → 调内核 | 同 |
| 贸易条款正列 | 字段清单 + 校验规则 | alembic 迁移 + CRUD | 同 |
| 列表筛选（quote/inquiry） | WHERE 片段拼装 | 执行 | 同 |
| 反查（报价单 → 已生成单证） | SQL + 结果整形 | 执行 | 同 |
| 状态机 | 迁移表 + 校验 | 执行 | 同 |

**预期效果**：这两个接口族的业务逻辑**只写一遍**；两侧各只写约 10–20 行"取数 + 调内核 + 返回"。

## 5. 第 3 步：CI 门禁（防复发）

| 检查 | 内容 | 失败条件 |
|---|---|---|
| **① 路由一致性** | `scripts/_drift_audit.py` 转正为 `scripts/route-parity-check.py`，比对两侧路由集合 | 出现**白名单之外**的新差异 |
| **② 双端契约** | 对核心接口（单证全链路 + 认证）断言"同一请求 → 两侧响应结构一致" | 结构不一致 |
| **③ 内核一致性** | 若走 Plan B（复制），校验 `worker/src/_common/**` 与 `backend/common/**` 逐字节一致 | 不一致 |
| ④ 反查守护 | 断言"前端调用的接口在线上都存在"（A 类一旦出现新增即失败） | 新增死链 |

**白名单机制**（关键设计）：

```
scripts/route-parity-allowlist.json
{
  "knownMissing": ["POST /api/v1/outreach/campaigns", ...],   // 存量 80 项，只允许删
  "knownExtra":   ["GET /api/v1/market/ports", ...]           // 存量 10 项，只允许删
}
```

CI 校验规则：
- 实际差异 ⊆ 白名单 → 通过
- 实际差异 ⊃ 白名单 → **失败**（新增漂移）
- 实际差异 ⊂ 白名单 → 通过，并**提示可以缩减白名单**（债务燃尽）

每次收敛一项就往回删一项，**白名单长度就是债务燃尽曲线**。

## 6. 第 4 步：存量差异分批收敛

| 类别 | 数量 | 处置 | 时机 |
|---|---|---|---|
| **B 类 反向漂移**（线上有、主线无） | 10 | **反向补齐到 orchestrator 主线**（已是既成事实，防止重新部署时丢失） | W2 |
| **A 类 前端调、线上无** | 33 | 先按业务状态分类：**已启用** → 补后端（走共享内核）；**未启用** → 摘前端入口或加灰发开关 | W2–W4 分批 |
| **C 类 死链** | ~6 | 补后端 或 摘入口（业务定） | 按需 |
| **D 类 未上线功能** | ~47 | 按产品路线图排队，**不在本方案范围** | 不处理 |
| **`customers/{}/stage` 方法分叉** | 1 | 核对前端用哪个 → 统一 | W1（小但明确的契约 bug） |

> **A 类必须由你按业务状态标注"已启用/未启用"** —— 这是业务判断，不是技术判断。
> 把所有 A 类都当事故去补后端，会造成大量无效工作量（有些工位还在开发中）。

## 7. 第 5 步：运行时收敛评估（中期，不阻塞交付）

若希望**彻底消除双份**（而不只是"新增不再重复"），唯一路径是让线上跑与开发版相同的代码，
即**换掉 Pyodide 运行时**（例如 Cloudflare Containers 跑完整 FastAPI + SQLAlchemy，
或部署到常规容器平台）。

评估维度（产出结论再定，不预设答案）：
- 冷启动与常驻成本 vs 当前 Pyodide 方案
- Hyperdrive 连接复用是否仍适用
- 迁移工作量（路由/中间件/认证/静态资产托管）
- 回滚与灰度方案
- 是否值得（取决于 §6 收敛后残留的差异量）

**建议节奏**：等 W1–W4 落地 + 白名单缩到一定规模后再评估。现在评估会得出"成本巨大、收益不确定"的结论。

## 9. 明确不做什么（边界，防止方案失控）

| 不做 | 原因 |
|---|---|
| 重写 orchestrator 的数据访问层（SQLAlchemy → asyncpg） | 大爆炸式改造，风险极高、收益低 |
| 一次性补齐 80 个缺失接口 | 其中 47 个是"未上线功能"，不是债 |
| 把 worker 改造成"从 orchestrator 自动生成" | 生成器本身的复杂度会超过它解决的问题；先做内核分层 |
| 现在就上 Cloudflare Containers | 评估结论未出，且会拖慢本次交付 |
| 动前端既有页面的调用方式 | 除"摘掉死链入口"外不改，避免引入新风险 |

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Worker 无法 import 共享包（Plan A 失败） | 内核方案受阻 | Plan B（构建时复制 + CI 校验）；W0 先验证再推进 |
| 内核提前抽象过度 | 变成"为架构而架构" | 只抽**已被两侧重复实现**的逻辑（有漂移实证的），不为未来预留 |
| 白名单被当"免死金牌" | 债务固化 | 每波强制缩减；CI 对"差异 ⊂ 白名单"给出**缩减提示** |
| A 类补齐工作量超预期 | 拖慢交付 | 先业务分类；"未启用"的只摘入口，不补后端 |
| 改快照结构影响历史单据 | 已签发单据渲染异常 | 快照只**增字段不删字段**；渲染层对缺失字段容错（已有 `_RenderDict` 空串兜底） |
| 两侧共用 SQL 但行为仍不一致 | 假收敛 | 双端契约测试（§5 ②）作为最终判据 |
