## 一、这次交付了什么（业务语言）

### 1. 单证工位真正可用了

以前的状态是「后端能存一条单证记录，但**打不出单据**」——线上运行的精简版后端刻意不带模板引擎，
19 类模板只存在于开发环境，点预览就是 404。

现在渲染搬到前端，**18 类外贸单据可以真正开具、预览、打印**：

| 分组 | 单据 |
|---|---|
| 出口商自制（我方出具，可直接发客户） | 报价单 · 形式发票 PI · 销售合同 · 商业发票 · 装箱单 · 装运通知 · 汇票 · 受益人证明 · 非木质包装声明 · 重量单 · 质量证明 · 制造商证明 |
| 第三方签发（本系统出申报/申请信息） | 提单 · 原产地证 · 保险单 · 报关资料 · 熏蒸证明 |
| 通用 | 自定义声明 |

每类单据的**列是固定的**（按海关/银行审单要求），不随数据漂移：
商业发票一定带 HS Code、一定**不**出现毛净重列（那属于装箱单）；装箱单一定带包装、毛净重、体积。

### 2. 单据会自动继承上游数据（业务连贯性）

```
询盘 → 报价单 → 订单 → 单证
              ↑        ↑
           谈定条款   自动继承
```

- 开单时选择上游订单/报价单，**货物、规格、HS Code、数量、单价、金额、贸易术语、付款方式、
  装卸港、唛头、原产国**全部自动带入，不用重填。
- 开单瞬间把上游内容**冻结成快照**：以后订单被改动，**不会**污染已开出的单据。
- 草稿阶段可以「从上游重新带入」；**签发后彻底冻结**（已签发单据是法律凭证）。
- 手动在单据上改过的内容优先级最高，不会被自动带入覆盖。

### 3. 补上了「单据没法用」的几个硬缺口

| 缺口 | 后果 | 现况 |
|---|---|---|
| 卖方抬头无处配置 | 每张单据的卖方信头是**空白**，等同废纸 | 新增「设置 → 企业信息」：公司英文名/地址/联系方式/收款银行/SWIFT，保存一次全部单据自动带入 |
| 贸易条款无处存 | 报价谈定的 Incoterm/付款方式无法继承，单证要手工重填 → 信用证下就是「不符点」 | 报价单与订单新增 6 个正列，且报价转订单时自动继承 |
| 上游快照没带规格 | 发票/装箱单的规格、HS Code、毛净重全空 | 快照补 `spec_snapshot` |
| 买方只有公司名 | 收货人缺地址/联系人 → **清关会出问题** | 快照带出客户地址与主联系人电话/邮箱 |
| 单证类型只有 9 种 | 另外 9 类模板**根本开不出单**（接口报 422） | 补齐到 18 种（本地与线上同步） |

### 4. 出单前的合规提示

开单预览时会明确列出「**还差哪几项必填**」（用中文说明，如「HS Code」「收货人地址」），
而不是让你盯着一张空白单据猜是没填还是系统没带过来。必填齐全才提示「可签发」。

### 5. 交付方式

- **打印 / 导出 PDF**：走浏览器打印，版面与屏幕所见一致（A4 分页由浏览器处理，更可靠）。
- **批量合并打印**：一票货的「发票 + 装箱单 + 提单」一次打完，每份之间自动分页，不会漏打重打。
- **单证台账导出**：CSV（带 BOM，Excel 双击不乱码）与真正的 `.xlsx`。
- 单份单据可**下载 HTML** 留档。

### 6. 顺带把「订单」和「出货」两个工位建起来了

- **订单**：从报价单转订单（继承货物、币种、贸易条款）；维护贸易条款；状态流转。
- **出货**：从订单建出货单；录船名/航次/提单号/集装箱号/ETD/ETA/装卸港/收货人；出运状态推进。
- 这两个工位的字段正是提单、装运通知、报关资料要印的内容，录一次后开单证不用再问货代。

## 四、这次怎么保证「迁移没有偷偷改坏东西」

渲染器从 Python 搬到 TypeScript，属于最危险的一类改动：**看着差不多，实际金额千分位、
日期写法、某列缺失已经变了**——肉眼根本发现不了，但海关/银行审单就是按这些细节退单。

做法：迁移**先冻结 Python 版的输出**（18 份样例 HTML）作为基准，TypeScript 版必须与之**逐字节一致**。

这道关卡实际拦下了两处真实偏差：

1. Windows 文本模式写出的 CRLF 与模板内部的 LF 差异；
2. **「看起来像数字的字符串」被误当金额格式化** ——
   HS Code `7314410000` 被渲染成 `7,314,410,000.00`。这在海关审单里就是「不符点」。

## 五、防「再次遗漏 / 不同步」的机制

以前的问题不是「没做」，而是**改了这边忘了那边**。现在由机器守：

| 规则 | 防的是什么 |
|---|---|
| R0 | 事件类型在前端/后端/文档三处不一致 |
| R1 | 报价请求响应的字段前后端不一致 |
| R2 | 工位元数据（侧边栏/面包屑的来源）前后端不一致 |
| R3 | 单证类型在「模板 / 类型字典 / 编号前缀」三处不一致（漏登记会让单号变成 SA-202609-0001 这类无含义编号） |
| R4 | **线上 Worker 与本地实现不一致**（单证类型集合、编号前缀、单号字段映射） |

> **R4 是专门防「手工同步漏掉」的**：本地能开单、线上报 422，或反过来线上能开、本地开不出，
> 现在会直接 CI 失败并指出具体差在哪一项。

每条规则都做过**对抗测试**（故意改坏→确认能报错→改回），避免出现「校验永远通过」的假安全。
