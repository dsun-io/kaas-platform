## 二、根因链（已闭合）

```
① 首屏最先的几个请求绕过 MSW（未被 Service Worker 接管）
② 直连 Next dev server → 命中 /api/v1/* rewrite → rewrite 指向页面源
   → 自己代理自己（EADDRINUSE）→ 返回 500 或永久挂起
③ /auth/me 拿到 500 → AuthProvider catch → 清会话 → user === null
④ route-guard 在 adminOnly && !isAdmin 时渲染「您没有访问此页面的权限」
⑤ 其余请求拿 500 → 页面进错误边界「页面加载异常 / 后端繁忙」
⑥ 挂起的连接让 waitForLoadState('networkidle') 永不满足 → 用例超时
```

**同一条链解释了全部看似无关的现象**：权限文案、错误边界、`networkidle` 超时、
以及"每轮通过数都不一样"（竞态）。此前它们是四条各自调查的线索。

## 三、找到根因用过的三个仪器（可复用）

| 仪器 | 作用 |
|---|---|
| `onUnhandledRequest: "warn"`（MSW） | 让**未被 mock 匹配**的请求在控制台被点名（原先是 `bypass`，**静默**，所以坑拖了很久） |
| fixture 转发 `page.on('console')` | Playwright **默认不转发页面 console 到 stdout**，不转发就永远看不到上一条 |
| **`response.fromServiceWorker()`** | **决定性**：直接回答"这个响应是不是 MSW 给的"，比从 dev server 的反向报错反推可靠得多 |

第三个仪器一上线就**直接点名**了绕过者：

```
[绕过MSW] GET  /api/v1/auth/me     -> 500
[绕过MSW] GET  /api/v1/customers?  -> 500
[绕过MSW] POST /api/v1/events      -> 500
```

**即"首屏那一批"，且返回 500** —— 因果链就此闭合。

## 六、已做的关键修复：Playwright 兜底路由（`8927fba`）

**原理**：**被 Service Worker 处理的请求根本到不了 `page.route`**
（Playwright：SW 拦截的请求不经 `page.route`）。所以
`page.route('**/api/v1/**')` **只会看到漏网的请求**，且**不会抢走 MSW 的活**。

**做法**：`/auth/me` → 返回与 MSW 同一个管理员身份；其余 → `200 {}`（比 500 好，不崩不挂）。

**效果**：

```
[兜底路由] GET  /api/v1/auth/me
[兜底路由] GET  /api/v1/me/workstations
[兜底路由] GET  /api/v1/teams/me
[兜底路由] POST /api/v1/events
[兜底路由] GET  /api/v1/customers?
```

- **`[绕过MSW] ... -> 500` 归零** ✅（自代理的 500 与挂起消失）
- 顺带证实：绕过的**不只是** `auth/me`/`customers`/`events`，
  `/me/workstations` 与 `/teams/me` **同样绕过** —— 即"首屏那一批"

**边界**：兜底路由**只让 e2e 稳定，不改应用行为**（生产不走 MSW，也不走 `page.route`）。
**应用侧根因（首屏请求未受 SW 控制）仍未修复**，只是不再污染测试结果。

## 八、待办

### 8.00000 🎯 根因锁定：绕过的请求**全是 `xhr:`**（axios 的 XHR adapter）

用网络层探针（`page.addInitScript` 包住 `window.fetch` 与
`XMLHttpRequest.prototype.open`）实测，答案完全对得上：

```
[网络探针] xhr:GET  /api/v1/auth/me
[网络探针] xhr:GET  /api/v1/customers?
[网络探针] xhr:GET  /api/v1/me/workstations
[网络探针] xhr:GET  /api/v1/teams/me
[网络探针] xhr:POST /api/v1/events
```

**绕过的这 5 个请求全部是 `xhr:`**；而 MSW **拦得住**的那一条
（`GET /customers?_rsc=…`，Next 的 RSC prefetch）是 **`fetch`**。

> **结论：MSW 的 Service Worker 拦不住这批走 XHR 的请求。**
> 这与前面几轮的观察全部吻合：MSW 会报页面请求的缺口、却不报 `/api/v1/*` 的
> —— 因为那些请求**根本没经过它**。

（这也是 MSW + axios 的常见坑：axios 浏览器端默认用 XHR adapter。）

### 8.000001 试过的修法：让 axios 在 mock 模式改用 fetch adapter —— **未生效，已回退**

在 `apiClient`（`lib/api/client.ts`）的 `axios.create` 里加
`adapter: isMockMode ? "fetch" : undefined`，再关掉兜底路由实测：

```
[绕过MSW] GET  /api/v1/auth/me     -> 500
[绕过MSW] GET  /api/v1/customers?  -> 500
[绕过MSW] POST /api/v1/events      -> 500
```

**绕过依旧**（1 passed / 1 failed）→ 按纪律**已 `git checkout` 回退**
（不在核心 HTTP 客户端里留一个「收益未验证」的改动）。

**下一轮要做的第一件事（很关键、也很便宜）**：重跑一次**带网络探针**的实验，
看那几行是 `xhr:` 还是变成了 `fetch:` ——

- 若仍是 `xhr:` → 说明 `adapter` 这个配置**根本没生效**

- 若变成 `fetch:` 却**仍然绕过** → 那"XHR vs fetch"这条解释就不完整，

### 8.0000 决定性对照：MSW **拦得住页面请求，拦不住 `/api/v1/*`**

把上一步那"1 条缺口"的**内容**打出来（此前只数了条数），对照就出来了：

| | 请求 | 结果 |
|---|---|---|
| **MSW 拦到了**（并报缺口） | `GET /customers?_rsc=1eq7f` —— **Next 的 RSC prefetch**，一个**页面**请求 | 报缺口（无对应 handler）✔ |
| **MSW 完全没拦到** | `/api/v1/auth/me`、`/api/v1/customers?`、`POST /api/v1/events` | 直连网络 → **500** ✘ |

**同一个页面、同一时刻**：MSW 拦得住**页面**请求，却拦不住 `/api/v1/*`。

> 这**排除**了"SW 没起作用"这一整类解释 —— SW 明明在工作（它拦了 RSC）。
> 问题被推到更具体的一层：**这几个 `/api/v1/*` 请求是怎么发出去的？**

#### 下一个探针（已想好，很便宜）

在 fixture 里用 `page.addInitScript` **包住 `window.fetch` 与
`XMLHttpRequest.prototype.open`**，记录它们看到的 URL：

- 若**看到** `/api/v1/*` → 是应用发的，那就要问"为什么 SW 不拦它"
  （可能与该请求的 `mode`/`credentials`/adapter 有关）
- 若**看不到** → 这些请求**不是页面里 `fetch`/XHR 发的**，
  那就要找真正的发起方（这也是一个明确得多的方向）

这条对照是这轮最有价值的产出：**它把"SW 控制权"这条走了好几轮的线彻底关掉，
换成一个能一步定性的新探针。**


### 8.000 探针实测：**"SW 没控制本页"也被证伪**，且兜底路由其实是**抢占**而非"只接漏网"

本轮把探针接上（`worker.start()` 成功与否、`controller`、`getRegistrations()`），
并用 `E2E_FALLBACK=0` 做了对照实验。结果：

| 观测 | 值 |
|---|---|
| `worker.start()` | **resolve**（没有 FAILED 日志） |
| Service Worker 注册 | **`http://localhost:3000/\|active`** ✔ |
| `navigator.serviceWorker.controller` | **`true`** —— **页面确实被 SW 控制** ✔ |

**所以"SW 没控制本页"这个假设也不成立。**

#### 对照实验（关键）

| 观测 | 兜底 ON | 兜底 OFF |
|---|---|---|
| `[绕过MSW] ... -> 500` | 无 | **回来了** |
| MSW 报"未匹配"缺口 | **0** | **1** |
| SW 控制本页 | `true` / `active` | 同 |

**两条结论**：

1. **兜底路由确实"先于" Service Worker 拦截** —— 所以它把 MSW 的活**抢走了**。
   > 我上一轮说它是"加法、只接漏网的"，**这个判断是错的**：
   > `page.route` 在 SW 之前生效，于是它拦下了**全部** `/api/v1` 请求
   > （缺口因此从"有"变成 0）。虽然它让 500 消失（表面变好），
   > 但**代价是 MSW 的 mock 全都不生效了** —— 页面拿到的只是 `200 {}`。
2. **但没有它时，`auth/me`/`customers`/`events` 依然不被 MSW 处理**（照样 500）。
   即：**兜底路由既不是解药、也不是病因**，而是一层**掩盖**。

#### 收窄后的真问题

> **SW 已注册、已 active、已控制本页，MSW 也报得出缺口（1 条）——
> 但 `auth/me`、`customers`、`events` 这三个请求就是不经过它。**

这意味着"SW 控制权"这条线**也走不通**了。下一个该查的方向：

- 那 1 条"缺口"具体是**哪个**请求？（把它打出来，就能对照出"被拦的"与"没被拦的"差在哪）
- 这三个请求的**发起方**是否不同（例如 PRC/RSC、或某个不走 `fetch` 的路径）
- `MSW` 的 handler 表在 e2e 环境下**是否为空**（若空，则所有请求都不匹配 →
  但那样缺口应该是 N 条而不是 1 条，故暂不采信）

#### 本轮保留的改进

- `MswProvider` 的 `.catch` **不再静默**（打印 `[MSW门] start FAILED:`）——
  与 `bypass` → `warn` 属同一类修正：**失败必须有声音**
- 保留两条探针（`controller` / `registrations`）与 `E2E_FALLBACK` 开关，
  便于下一轮继续对照

### 8.0 ⚠️ 重新基线化的**前置条件**（本轮实测发现，必须先解决）

兜底路由虽然消灭了 500/挂起，但它对**非 `auth/me`** 的请求只返回 **`200 {}`**
—— 这会让页面**渲染不出任何数据**：

> `listData.items` 是 `undefined` → `listData?.items?.length === 0` 为 **false**
> → **空态不显示**；`listData?.items?.map(...)` 渲染 **0 项**
> → **卡片也不显示**。

实测：把 `customers.spec.ts` 按现役 UI 改好（卡片 + 空态 + 去掉 `networkidle`）后，
结果 **1 failed / 2 skipped（0 passed）**，而**原版是 1 passed** ——
**改动让结果变差，已按纪律回退**。

（本轮同时验证到：**应用级错误与 500 均为 0** ✓ —— 即兜底路由该做的部分做到了。）

**所以顺序必须是**：

1. 让绕过 MSW 的请求拿到**正确形状的数据**（两条路任选其一）：
   - **A. 修应用侧根因**（首屏请求未受 SW 控制）→ MSW 正常供数，最干净
   - **B. 兜底路由返回真实形状**：复用 `mocks/data/factory` 的数据，
     为绕过的端点（`auth/me`、`me/workstations`、`teams/me`、`events`、`customers`）
     给出与 MSW **一致的响应**（代价：多一份 mock，需防漂移）
2. **然后**才做选择器重新基线化 —— 否则改了也只是把"选择器不对"换成"没数据"。

> 这一条正是上一轮"先改选择器会失败"的**确切原因**，现在有了证据。

1. **选择器重新基线化**（用户已裁决）——现在才有意义：兜底路由已让页面拿到身份。
   按第五节的清单逐页改：`customers`（卡片）、`events`（无 table）、
   `admin/gray-release`（改断言）、`dashboard`（「7天」）、`quotations`（路由已不存在 → 改指 `/quotes` 或退役）
2. `audit-log` 与 `dashboard` 剩余几条（期望文案都在）需单独查
3. **应用侧根因未修**：首屏请求未受 SW 控制（SW 注册发生在本次加载期间，
   本次加载的请求不受它控制）。若要让 mock 模式在**真浏览器里也可靠**，
   可考虑让 SW 在 hydration 之前注册，或改用 `serviceWorkers: 'block'` +
   Playwright `page.route` 全面替代 MSW
