# 产品 / 询盘 / 订单 · 傻瓜化优化方案（2026-10-22）

> 性质：**设计稿，未动代码**。目标是把用户 2026-10-22 提出的 5 个问题一次说清：
> 产品图片归位、产品 key 是否展示、规格参数太难、询盘不能多产品、手工订单不能录信息/传单证。
> 同时给出全站配置页“去技术名词”的统一口径、工作量、风险与验收标准。
>
> 现状取证：mock 模式实拍 `frontend/artifacts/products-current.png`、
> `products-selected.png`、`products-editor.png`、`customer-detail.png`、`orders-create.png`；
> 代码位置见每节“现状”。

## 0. 一句话结论

| # | 用户问题 | 设计结论 |
|---|---|---|
| 1 | 产品图片要归到各个产品中 | 把「图片与基础信息」和「定义」两个大区块合并成**一个产品一张卡 / 点开即产品详情**；图片成为该产品详情的第一块，卡片直接显示主图缩略图。后端本来就按产品存图，只改信息架构。 |
| 2 | 为什么显示产品 key | key 是**内部稳定编号**（报价/单证/图片/定价数据靠它关联），不能删；但**普通界面一律不展示**，新建产品自动生成。解释见 §2。 |
| 3 | 规格定义/参数太难 | 普通界面只留**业务项**：利润率、税费、成本口径、规格参数（名称/单位/默认值/范围）、可选档位、包装费、HS 编码；公式/JSON/列/校验/底层结构全部收进**平台管理员折叠的高级设置**。 |
| 4 | 添加询盘不能加多个产品 | 一条询盘支持**多个产品行**：`cust_inquiries` 增加 `items jsonb`，旧字段继续保留做兼容；弹窗改成可增删的产品行。 |
| 5 | 手工订单不能录信息/传单证 | 手工建单改成**四步向导**：客户与来源 → 订单信息（日期/币种/贸易条款）→ 货物明细 → 单证附件；后端 `POST /orders` 已支持这些字段，补“订单附件”文件能力即可。 |

## 1. 共同原则：什么叫“傻瓜配置”

1. **默认值优先**：打开即可用，空着也能出结果；只有影响算价/单证的字段才必填。
2. **业务语言**：界面上只出现“产品、规格、档位、利润率、包装费、单证、附件”等词；
   不出现 API、JSON、token、spec、key、租户 ID、环境变量、端点、公式、表达式。
3. **渐进披露**：底层能力不删除，收进「高级设置（仅平台管理员）」折叠区；
   普通成员永远看不到，平台管理员需要时仍可维护。
4. **一处维护、多处引用**：图片/基础信息/规格仍在产品工位维护，报价与单证只引用。
5. **不静默兜底**：保存失败、上传失败、规格不合法必须给出人话原因与下一步动作。
6. **改文案不改能力**：全站清理以“换说法 / 折叠 / 给示例”为主，不删功能、不改请求。

### 术语替换表（全站配置页统一）

| 现在会看到 | 改成 |
|---|---|
| 产品 Key / 产品 key | 不展示；内部自动编号（仅管理员高级设置只读） |
| spec / 规格 JSON / JSON 文本框 | 产品规格；原始数据（仅管理员高级设置） |
| 数值参数 / numeric_inputs | 规格参数 |
| 变体档位 / variants | 可选档位 |
| 派生公式 / 表达式 / expr | 计算规则（仅高级设置） |
| 列 / 校验 / 空间扣减 | 报表列 / 校验规则 / 体积扣减（仅高级设置） |
| 参数 / 说明 / 常量 | 参考参数 / 说明 / 固定值（仅高级设置） |
| 租户 / 租户 ID | 空间 / 团队（ID 列直接隐藏） |
| API 令牌 / REST API / MCP / Bearer | 系统对接密钥；外部系统/自动化工具对接用 |
| token 用量 | 用量 / 费用 |
| 环境变量 ENV:xxx / RESEND_API_KEY | “发信服务：已配置/未配置” |
| 端点 / endpoint / 对象路径 | 接口 / 归档文件 |
| 字段 | 信息项 / 内容项 |
| 原始 JSON / payload | 默认折叠为“查看详情（一般不需要看）” |

## 2. 产品图片归到产品里（问题 1）

### 现状（证据）
- 后端 `file_objects.owner_type='product', owner_id=product_key` 已经**按产品存图**；
  `GET /api/v1/products/{product_key}/media` 也按产品返回。
- 问题在**信息架构**：`/products` 上面是一块“产品选择器 + 基础信息 + 图片”，
  下面又是一块完全独立的“产品定义管理”表格；图片看起来像公共图库，
  产品 key、profit_mode 等内部字段反而站在最显眼的位置。

### 目标信息架构
```
产品
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ [主图缩略图]  │ │ [主图缩略图]  │ │ [主图缩略图]  │
│ 勾花网        │ │ 牛栏网        │ │ 鹿网          │
│ 平台内置 · 3 张│ │ 我们自定义 · 0张│ │ 平台内置 · 1张 │
└──────────────┘ └──────────────┘ └──────────────┘
        ↓ 点一张卡，下面展开该产品的详情
┌─ 勾花网 ─────────────────────────────── [保存] ─┐
│ 产品图片：大图网格 + 上传/命名/类型/排序/设主图    │
│ 基本信息：材质/表面处理/用途/包装/产地             │
│ 规格与价格：利润率、综合税费、成本含税口径          │
│             规格参数（客户报价时填写）              │
│             可选档位（表面处理等）                  │
│             包装费 / HS 编码                       │
│ ▸ 高级设置（仅平台管理员）                          │
└────────────────────────────────────────────────┘
```

### 交互细节
- 卡片主图取该产品第一张主图；没有图用产品图标占位，不再出现“图片在别处”的错觉。
- 上传图片后立刻出现在**当前产品**详情里；不跳页、不切 tab。
- 图片操作保留：命名、类型（生产/尺寸/重量/成品/其它）、上移下移、设主图、移除、复制临时链接。
- 移除图片叫“移除图片（可恢复）”，不写“下线”；不展示存储类型（inline/s3）。

### 不做的事
- 不新增“产品图库”全局页；不把不同产品的图片混在一起。
- 不改后端图片归属与团队隔离。

## 3. 产品 key：有什么设计用意，怎么处理（问题 2）

### 它是什么
产品 key（`chain_link` / `field_fence` / `deer_net`）是**机器用的稳定编号**，被这些地方引用：
- 文件表：`file_objects.owner_id = product_key`（产品图片归属）；
- 产品定义表：`tenant_products.product_key`（团队自定义覆盖靠它对应系统产品）；
- 定价数据：`spec_hash` 前缀 = 产品 key（成本档位按产品查）；
- 报价行/单证快照：历史报价、单证要能追溯到“当时是哪个产品”。

### 为什么不能直接删
产品显示名会改、会翻译（中文名/英文名），key 不能跟着改；否则历史报价、单证、
已上传图片、定价数据会全部失去关联。**key 是稳定锚点，不是给人看的字段。**

### 设计
- 普通界面**完全不展示 key**：产品卡、详情、表格、表单都不出现。
- 新建产品时由系统自动生成（英文名转 slug，冲突时加序号；取不到英文名用
  `product_<时间戳>`），用户只填“产品名称 / 英文名”。
- 系统内置产品“复制成我们自己的”时，沿用同一个 key 作为团队覆盖（不新增产品）；
  从产品模板新建一个**额外产品**时生成新 key。
- 平台管理员的高级设置里只读展示 key，供排障；普通成员不可见。
- 文档/单证展示用产品名称，不展示 key。

## 4. 规格定义与参数：两层设计（问题 3）

### 现状
`/products` 的“定义”区直接暴露：
`产品 Key / profit_mode / 利润率 / 税费系数 / 成本口径 / 规格定义`
以及 `ProductSpecEditor` 的五个 tab：
数值参数、派生公式、列/校验/扣减、参数/说明/常量、高级 JSON。
对非技术同事来说，这等于要求他理解报价引擎的数据结构。

### 普通层（所有人可见）
| 区块 | 控件 | 落到数据 |
|---|---|---|
| 价格设置 | 售价利润率（%）、综合税费（%）、成本口径（含税/不含税） | `spec.profit_value` / `spec.misc_fee_rate` / `cost_basis`，同时回写产品行，修掉“两处不同步”的旧问题 |
| 规格参数 | 行：参数名称、单位、默认值、最小值、最大值；参数名称/单位只读，范围可改 | `spec.numeric_inputs[]`（key 保留，不再让用户看见） |
| 可选档位 | 组：表面处理 / 材质…；值以标签形式增删 | `spec.variants[]`（选项 `name` 保稳定，标签给人看） |
| 包装费 | 包装名称、方式、默认金额；可选“按规格分档” | `spec.packaging[]` |
| HS 编码 | 一行多个，逗号分隔 | `spec.hs_codes[]` |

> 普通层**不允许增删规格参数**（参数 key 被公式引用，乱加会算出错价）；
> 要改参数结构，走高级设置。可选档位可以自由增删，因为它只影响可选值/定价数据。

### 高级层（仅平台管理员，默认折叠）
- 保留现有 `ProductSpecEditor` 全部能力（数值参数/公式/列/校验/扣减/参数/说明/常量/高级 JSON）。
- 入口文案：“高级设置（仅平台管理员）· 修改前请先备份/确认”。
- 普通成员 DOM 里不渲染高级区（不是 CSS 隐藏）。
- 保存时业务层与高级层共用同一份 spec：业务层改业务字段，高级层改底层字段，互不覆盖对方未知字段。

### 系统产品 vs 自定义产品
- 系统内置产品：普通层只读，显示“平台内置规格”；按钮“按我们的规格自定义”会复制一份
  团队覆盖（同 key），之后可编辑业务层与高级层。
- 自定义产品：可编辑、可删除；删除前确认，历史报价/单证保留快照。
- “新增产品”不再提供空白新建（空 spec 没有计算规则，一报价就报错）：
  改为“从现有产品复制一个”，选模板 → 填名称 → 生成新 key。

## 5. 询盘支持多个产品（问题 4）

### 现状
- `cust_inquiries` 表只有单组字段：`product_name_raw / quantity / quantity_unit / application / notes`。
- “添加询盘”弹窗只有一个产品名称输入框，一次只能录一个产品。
- 客户详情里一条询盘卡片只显示一个产品。

### 方案 A（推荐）：一条询盘多个产品行
```
添加询盘
渠道 [邮件 v]   备注 [....................]
产品 1  [勾花网 v / 可手输]  规格 [2.5mm 热镀锌]  数量 [1000] 单位 [㎡] 用途 [围栏]
产品 2  [牛栏网 v / 可手输]  规格 [1.8m 高]       数量 [500]  单位 [m]  用途 [牧场]
[+ 再加一个产品]
[提交]
```

数据设计：
- 迁移：`ALTER TABLE cust_inquiries ADD COLUMN items jsonb NOT NULL DEFAULT '[]'`。
- 每行：`{product_key?, product_name_raw, spec_text?, quantity, quantity_unit, application, notes}`。
- **兼容旧数据**：`product_name_raw / quantity / quantity_unit / application / notes` 继续保留；
  新建时把第一行同步写进旧字段（或写汇总名），旧报表/链式分析不需要改。
- 读取：`row_to_inquiry` 增加 `items`；`items` 为空时用旧字段合成一行，历史询盘照常显示。
- API：`POST /customers/{id}/inquiries` 接受 `items[]`（旧标量字段仍兼容）；
  `PATCH /inquiries/{id}` 支持改 `items`。
- 前端：客户详情卡片显示产品标签/行；`product_name_raw` 只作为摘要。
- 报价：一条询盘仍对应一个 `quote_orders.inquiry_id`；报价单本身支持多行产品，
  所以“一张询盘 → 一张多产品报价”天然成立。若团队习惯一产品一报价，也可在报价工作台拆行。

### 方案 B（备选，不做迁移）
一个弹窗填多个产品行，提交时循环创建多条询盘（每条一个产品）。
优点：零数据库改动；缺点：一个客户询盘会变成多个询盘号，客户页更碎。**不推荐。**

## 6. 手工订单：能录信息、能传单证（问题 5）

### 现状
“手动新建订单”表单只有：客户、关联报价（可选）、币种、备注。
后端 `POST /orders` 其实已支持：`order_date / delivery_date / items[] / incoterm /
payment_terms / port_of_loading / port_of_destination / shipping_marks / country_of_origin`；
订单详情也已有“贸易条款”编辑。缺的是**前端入口**和**附件能力**。

### 目标：四步向导（弹窗或抽屉）
1. **客户与来源**：业务客户（必选）、关联报价（可选，选中后自动带出币种/条款/货物行）。
2. **订单信息**：订单日期、交货日期、币种、贸易术语、付款方式、装运港、目的港、唛头、原产国、备注。
3. **货物明细**：产品（可从产品库选，也可手输）、规格说明、数量、单位、单价、金额；
   自动合计；允许“暂不填明细”（历史订单）。
4. **单证附件**：上传合同/PO/信用证/客户单证/其它（PDF、JPG、PNG），可多份、可跳过；
   每份可命名。提交后订单立即创建，附件随后上传；附件失败不回滚订单，提示“订单已建，附件重试”。
5. 完成页：显示订单号，按钮“查看订单 / 继续开单证（跳单证工位，带 order_id）”。

### 后端改动
- `POST /orders`：无需改（字段已支持）；前端按已有字段传参，补前端校验。
- 订单附件：
  - 共享内核 `backend/kaas_common/files/rules.py`：`OWNER_TYPES` 增加 `"order"`，
    附件用 `kind="other"`（允许 PDF/JPG/PNG），沿用 16MB 上限；
  - Worker 新增：`GET /api/v1/orders/{order_id}/files`、
    `POST /api/v1/orders/{order_id}/files`（multipart，命名 + 类型），
    复用现有 `_create_file` 与团队隔离；
  - 订单详情返回附件列表（或前端单独拉）。
- 单证：正式单证仍走“单证”工位；订单页提供“去开单证”入口，不把正式单证和附件混为一谈。

### 为什么不直接把附件塞进单证
正式单证（发票/装箱单/产地证）是模板生成 + 签发流程，需要 doc_type、渲染、版本；
合同/PO/信用证扫描件是**随单附件**，两者生命周期不同。分开更清楚，也避免把单证流程做复杂。

## 7. 全站配置页去技术名词（与上面 4 项同步做）

范围（用户已确认“所有配置类页面 + 产品模块”）：
- `/settings`：租户→空间/团队；隐藏租户 ID；环境变量名→中文服务名+配置状态；
  “重新加载 YAML 配置”→“重新加载产品配置”。
- `/settings/api-tokens`：改名“系统对接密钥”，说明“给外部系统/自动化工具对接用，
  普通成员不需要”；去掉 REST/MCP/Bearer/明文等词；创建/撤销流程不变。
- `/settings/ai-providers`：任务代码→中文业务名；“token”列→“用量/费用”；
  高级参数与原始返回默认折叠。
- `/pricing-data`、`/settings/tax-archives`：只保留“档位/成本/税率”业务词。
- `/leadgen`：不再显示 `RESEND_API_KEY` 等环境变量名，改“发信服务：已配置/未配置”。
- `/dashboard`：去掉 Token 消耗/P95/采样覆盖率，改为业务口径占位。
- `/kb`、`/receivables`：去掉“规格参数管理、公式配置、后端接口暂未提供参数”等实现细节。
- 技术详情页（审计日志/事件/灰度发布/AI 运行详情）：保留能力，原始 JSON / 路径 /
  事件代码默认折叠，按钮“查看详情（一般不需要看）”；操作名与资源名翻成中文。

## 9. 分阶段落地

> 每阶段都遵守仓库门禁；代码 + 文档 + 推送同步（AGENTS.md 规则 1）。

**P0 · 产品工位（最高优先，约 1.5 天）**
1. 产品卡 + 产品详情布局；图片进入详情；主图缩略图。
2. 隐藏 key；业务规格编辑器（价格/参数范围/档位/包装/HS）。
3. 系统产品“复制为自定义”；“新增产品”改为从模板复制。
4. 高级设置仅 `system_admin` 可见、默认折叠。
5. 更新 products 测试；Playwright 实拍验收。

**P1 · 手工订单（约 1 天）**
1. 四步向导 + 货物明细 + 贸易条款；创建后展示订单详情。
2. 订单附件（后端 owner_type=order + 两个端点 + 前端上传/列表）。
3. 单证工位深链（带 order_id）。

**P2 · 询盘多产品（约 1 天，含迁移）**

### 13.2 空白新建产品：如何补齐规则

空白产品没有 `derived` 公式，报价引擎算不出重量/体积/成本。设计为**三步兜底**：

1. **新建弹窗增加“计算方式”**（必选）：
   - 从现有产品复制计算规则（默认，选 勾花网 / 牛栏网 / 鹿网）；
   - 空白，稍后由平台管理员配置。
2. **空白产品保存后进入“待配置规则”状态**：
   - 产品卡与详情显示黄色提示“待配置计算规则，暂不可报价”；
   - “去报价”按钮禁用，避免用户以为系统坏了；
   - 平台管理员可见“配置计算规则”按钮，打开折叠的高级设置（原有完整编辑器）；
   - 普通成员不可见高级入口，只看到提示“请联系平台管理员补齐计算规则”。
3. **可随时从其他产品补规则**：详情里提供“从其他产品带入计算规则”，把目标产品的
   `derived / columns / invariants / space_deduction / constants / params` 复制过来，
   名称/图片/基础信息/自定义档位保持不变。
4. 判定“已配置”：`spec.derived` 非空（或产品有内置规则）。前端只用于提示与禁用报价，
   不新增数据库列，避免状态漂移。

### 13.3 订单金额、应收、实收与到账截图（新增需求 4）

用户口径：创建订单时要填各项金额；应收款用填写的金额和比例直接算；后期可填实收金额
（应收与实收可能对应不上）、收款时间、确认到账截图。

#### 订单金额构成
创建订单分四块金额：
- **货物金额**：由货物明细自动汇总（数量 × 单价；也允许直接改行金额）；
- **运费**：手填；
- **保险费**：手填；
- **其他费用**：手填（如佣金、包装附加）；
- **订单总额** = 货物金额 + 运费 + 保险费 + 其他费用（自动计算，只读展示）。

落库：
- `orders.total_amount` = 订单总额（沿用现有列，应收/报表都读它）；
- 新增 `orders.amount_breakdown jsonb` 保存四项金额，供订单详情回显与修改；
- 货物明细仍进 `order_items`。

#### 收款计划（应收按金额和比例自动算）
创建订单时“收款安排”区：
- 一键模板：`30% 定金 + 70% 发货前`、`50% + 50%`、`100% 预付`、`自定义`；
- 每行：期次类型（定金/尾款/其他）、比例（%）、金额、到期日、备注；
- 比例变化时金额自动 = 订单总额 × 比例（可手改，改金额时反算比例只做提示）；
- 提交时后端在**同一个事务**里创建订单、订单行、收款计划、应收台账；
- 校验：比例合计 ≤ 100%；金额合计与订单总额不一致时给出提示（允许差异，如运费后补）。

后端接口：`POST /api/v1/orders` 增加可选 `amount_breakdown` 与 `payment_plan[]`；
创建成功后立即生成 `receivables` 行（`status='unpaid'`），不再等到“确认订单”才建应收。

#### 实收登记（核心新能力）
新增表 `payment_receipts`（一次收款一行，允许同一期多次收款）：
```
id, tenant_id, order_id, schedule_id(可空), amount, currency,
received_date, fx_rate(可空), file_id(可空), notes,
created_by, owner_id, owner_scope, team_id, created_at
```
- 登记入口：收款计划行“登记收款”；实收金额默认 = 该期剩余应收，可改成实际到账金额；
- 必填：实收金额、收款日期；选填：实际汇率、备注、**确认到账截图**（PNG/JPG/PDF）；
- 到账截图走现有文件管线：新增 `payment_receipt` 归属类型，文件挂到 `file_id`；
- 允许多次登记；每次登记后重算：
  - 该期已收 = 所有 receipts 金额之和；
  - 期次状态：`pending` / `partial` / `paid`（`SCHEDULE_STATUS` 增加 `partial`）；
  - 应收台账：`received_amount` = 该订单所有 receipts 之和；
    `status` = `unpaid` / `partial` / `paid`；
  - 超收/差异：不强行改计划金额，页面显示“差异 = 实收 − 应收”，供财务核对。
- “对应不起来”的处理：`schedule_id` 可为空（一笔款暂不指定期次），
  或收款金额与期次金额不一致；页面提供“未分配收款”区与差异列。
- 兼容历史：已标记 `paid` 但没有 receipts 的旧计划，展示为“历史收款（无截图）”，
  实收金额取其 `amount`，不强制补录；新登记才写 receipts。

#### 接口清单
- `POST /api/v1/orders`：新增 `amount_breakdown`、`payment_plan[]`；
- `GET /api/v1/orders/{id}`：返回 `amount_breakdown`、`items`、`payment_schedules`、`receipts`；
- `GET /api/v1/orders/{id}/receipts`、`POST /api/v1/orders/{id}/receipts`；
- `POST /api/v1/payment-receipts/{id}/files`（multipart，到账截图）；
- `GET /api/v1/file-objects?owner_type=payment_receipt&owner_id={receipt_id}`（复用）；
- `POST /api/v1/orders/{id}/files`、`GET /api/v1/orders/{id}/files`（订单附件）。

#### 迁移
1. `cust_inquiries.items jsonb NOT NULL DEFAULT '[]'`；
2. `orders.amount_breakdown jsonb`；
3. 新表 `payment_receipts`；
4. `SCHEDULE_STATUS` 增加 `partial`（只需共享枚举 + 校验，无表约束）；
5. 共享文件规则 `OWNER_TYPES` 增加 `order`、`payment_receipt`（复用 `kind='other'`）。
