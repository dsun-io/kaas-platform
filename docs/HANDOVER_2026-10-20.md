## 10. 日常上线手册（2026-10-20 用户口径固化）

### 10.1 三个环境的形态与自动化程度

| 环境 | 形态 | 自动化 | 说明 |
|---|---|---|---|
| **开发** | 本地 Docker（PG/Redis/MinIO）+ uvicorn `--reload` + `pnpm dev` | 热重载，**边改边看** | 唯一日常开发形态；不触云（README §4/§13） |
| **预览** | 每 PR 一套：Neon 派生分支 + 独立 Hyperdrive + 独立 worker（workers.dev） | **全自动**：PR 打开/推送 → preview.yml 建资源/迁移/构建/部署/评论 URL；PR 关闭 → 自动回收。**无需任何手动操作** | 仅是验收工具，不拦发布链路 |
| **生产** | 单 Worker `kaas`（workers 关闭 dev 域名，只走自有域名） | **当前手动**（`workflow_dispatch` 触发 deploy.yml）；push main 只跑 CI 不部署 | 手动原因（用户口径 2026-10-20）：① GitHub 免费额度限制，每次 push 都烧 minutes；② S4 大范围改动落地初期需要可控。**恢复自动的条件**：额度稳定 + 系统稳定后，用户一声令下（把 `on.push` 加回 deploy.yml 即可，已预留注释位置） |

### 10.2 上线步骤（先干什么后干什么）

**标准流（默认，灰区/红区改动）：**
1. 本地开发验收（docker compose + 热重载 + 跑受影响侧门禁）
2. `feat/xxx` 分支 → 提交（中文 subject）→ push → **开 PR** → CI + 预览全自动
3. 点 PR 里的预览 URL 验收
4. 合并 main → CI 自动跑（测试，不部署）
5. **触发部署**：`gh workflow run deploy.yml --ref main`（或喊我代跑）→ 全自动链：构建前端 → 生产库 `alembic upgrade head`（`PROD_DATABASE_URL` 已配）→ S5-d 防污染断言 → 部署 → 冒烟 → 线上绑定断言
6. 看冒烟输出 + Cloudflare Metrics

**小改动直推（绿区：文案/样式/注释/测试）：** 直推 main → 等 CI 绿 → dispatch 部署。纪律：**CI 不绿不部署**；部署后翻车回滚 = `wrangler versions deploy <上一版>`，库回滚走 Neon PITR（不用 `alembic downgrade`）。
**红区（算价/鉴权/迁移/存储/订阅门禁）必须走预览。**

**首次大发布（当前 main 的 S4 后代码尚未上过生产）**：dispatch 前先做 §7 检查单的 secrets 一揽子（RESEND_API_KEY/S3 新密钥 + 冷启动基线 + 可选 Hyperdrive 关缓存），之后进入日常流。

### 10.3 预览的生命周期与"会不会漂移"

- **过时预览自动删**：PR 关闭 → teardown 全自动回收（worker/Neon 分支/Hyperdrive/R2+KV 前缀数据，幂等可复跑）。
- **PR 推新代码**：同一套预览资源原地重部署（URL 不变），代码永远=该 PR 最新提交。
- **不漂移的机制**：预览 Neon 分支**每次从 production 现场派生**（copy-on-write）→ 生产 schema/数据最新状态自动带入 → 再 `alembic upgrade head` 到代码 head；生产侧每次部署自动迁移收敛。代码（main）是唯一事实源，两头向它收敛。
- **诚实的边界**：已打开的 PR 预览**不会自动追平**期间生产的新迁移（派生快照停在开 PR 时）；PR 更新时代码会更新、库仍是初始派生。防冲突靠合并时的 CI 与迁移顺序，不靠预览。
- **上限**：Neon 免费层 10 分支 —— 同时大量开 PR 会建不出来（报错可见），关旧 PR 即回收。
- **三个漂移禁忌**（记住就永远不会失同步）：① 手动 `wrangler deploy` 旁路 CI；② 直接登录生产库手动 DDL；③ 改 `wrangler.jsonc` 绑定绕过 S5-d 断言。
