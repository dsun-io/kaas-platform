# 业务客户的历史报价 / 订单 / 单证 —— 包含关系与展示设计

> 2026-10-11 设计。目标：**在业务客户粒度下，按包含关系展示该客户的全部历史报价、订单、单证**。

## 1. 业务关系（用户确认）

```
业务客户
├── 报价 1（已接受）
│   ├── 单证：报价单 Quotation
│   └── 订单 A（由该报价生成）
│       └── 单证：PI / CI / PL / BL …
├── 报价 2（已发出）
│   └── 单证：报价单 Quotation          ← 未成单，报价和它的单证仍要能查到
└── 报价 3（草稿）
    └── 单证：报价单 Quotation
```

三条硬规则：

1. **一个客户有多个报价**（1:N）
2. **某些报价会生成订单**（报价 → 订单，1:N；一个报价可能分多次下单）
3. **每个报价都有对应的单证（报价单）；生成订单后还会有其他单证**（PI/CI/PL/BL…）
4. **单证要放在一起展示** —— 报价单和商业发票**不能分家**，都以"该报价/该订单的单证"形式贴在它所属的节点下

## 1.5 包含关系是**业务逻辑本身**的约束（不是查询层的补丁）

按业务的真实流程，层级是**自然产生**的，不该靠前端拼装、也不该靠查询时猜：

```
业务客户
  └── 报价            ← 唯一的"新建"入口；必须选客户
        ├── 报价单     ← 生成报价时自动产出（1:1），不是"用户再去单独建一张单证"
        └── 订单       ← 只能由报价"转订单"产生；客户/明细/条款/抬头全部继承
              └── 单证（PI / CI / PL / BL）  ← 订单推进过程中产出
```

由此推出的**写入侧硬约束**（落在业务逻辑与数据库约束里，不靠展示层兜）：

| 规则 | 落地方式 |
|---|---|
| 报价是唯一根入口，必须选业务客户 | `POST /quotes` 必填 `customer_id`，校验存在且属本团队 |
| 报价一定伴随报价单 | 创建/确认报价时**同一事务**产出 `trade_docs(doc_type='quotation', quote_id=报价)` |
| 订单只能来自报价 | 只能走 `POST /quotes/{id}/orders`（转订单）；新数据 `orders.quote_id` **NOT NULL**（DB 约束兜底） |
| 单证归属**二选一**（不按类型硬绑定） | `CHECK (quote_id IS NULL OR order_id IS NULL)`：报价单挂 `quote_id`；**由报价直接生成的 PI/CI 也挂 `quote_id`**（现实数据与既有写入路径就是这样）；由订单生成的挂 `order_id`；**都不给 = 只归属客户**（手动新建/导入，落 `direct`） |
| 客户沿层级继承 | 订单/单证的 `customer_id` 由父对象确定，**不单独再选**；`customer_name` 仅作开单快照 |

**这样"某个客户的往来记录"天然就是一棵树** —— 查询层不需要拼装，也不需要"孤儿"这个概念。

> 推论：前端"选已有业务客户"只发生在**报价**这一步；订单和单证都是跟着报价/订单走的，不该让用户重复选客户。

## 1.6 直接挂客户的单据（手动新建 / 导入已有数据）—— 正规路径，不是脏数据

业务明确要求：**支持手动新建订单/单证，也支持导入系统里已有的数据**。这类数据有个共同点 ——
**没有"报价"这一环**（历史订单可能根本没走过报价流程，历史单证可能只记了客户和金额）。

因此：

- **允许**手动新建订单/单证（以及批量导入），**但必须选业务客户**；
  报价/订单父对象**可选** —— 有就挂上（在树里出现在对应报价/订单下），没有就直接归客户
- 数据库约束只保证「**单据必须有客户**」，**不强制**「必须有报价/订单」——
  否则导入历史数据会被挡在门外，与业务要求直接冲突

读侧把它们放在 **`direct`（直接挂客户）** 分组，与"按报价组织"的分支并列：

```
业务客户
├── 报价 1 ─┬── 报价单
│           └── 订单 A ── 单证 PI / CI / PL / BL     ← 正常业务流程产生
├── 报价 2 ─── 报价单
└── 直接挂客户（手动新建 / 导入已有数据）              ← 正规路径
      ├── 订单 B ── 单证 …
      └── 单证 CI-…（无订单，仅归属客户）
```

`direct` 会**长期存在**（只要业务允许导入），不是"临时清理目标"，前端固定渲染这一块。


## 2. 现状缺口（必须补的两列）

| 关系 | 现状 | 缺口 |
|---|---|---|
| 客户 → 报价 | ✅ `quote_orders.customer_id` | — |
| 客户 → 订单 | ✅ `orders.customer_id` | — |
| 订单 → 单证 | ✅ `trade_docs.order_id` | 现有数据该列全为 NULL，需回填 |
| **报价 → 订单** | ❌ | `orders` **没有 `quote_id`** |
| **报价 → 报价单** | ❌ | `trade_docs` **只有 `order_id`，没有 `quote_id`** |
| 单证类型 | `trade_docs.doc_type`（实测只有 `pi`/`ci`） | 需要补 **`quotation`（报价单）** |

**要加的列**（迁移 `010`，与 `009` 的客户外键配套）：

```
orders.quote_id      BIGINT → quote_orders(id) ON DELETE SET NULL   -- 由哪个报价生成
trade_docs.quote_id  BIGINT → quote_orders(id) ON DELETE SET NULL   -- 报价单挂报价
+ 索引：(quote_id)、(customer_id, created_at DESC)
```

`trade_docs` 的归属规则（**二选一，不并存**）：

```
doc_type = 'quotation'  → 挂 quote_id（报价单属于报价）
其他类型               → 挂 order_id（PI/CI/PL/BL 属于订单）
```

## 3. 接口：树形返回（不是三个平行列表）

`GET /api/v1/customers/{customer_id}/records`

```json
{
  "customer": {"id": 7, "name": "Tim Trading", "team_id": 1},
  "counts": {"quotes": 3, "orders": 2, "documents": 6},
  "quotes": [
    {
      "id": 4, "quote_no": "QUO-202609-0004", "status": "accepted",
      "currency": "USD", "total_amount": 12300, "created_at": "2026-09-27T14:56:42Z",
      "documents": [
        {"id": 12, "doc_no": "QUO-202609-0004", "doc_type": "quotation", "status": "issued"}
      ],
      "orders": [
        {
          "id": 1, "order_no": "ORD-202609-0001", "status": "confirmed",
          "currency": "USD", "total_amount": 12300, "created_at": "2026-09-28T09:10:00Z",
          "documents": [
            {"id": 3, "doc_no": "PI-202609-0002", "doc_type": "pi", "status": "draft"},
            {"id": 2, "doc_no": "CI-202609-0001", "doc_type": "ci", "status": "issued"}
          ]
        }
      ]
    }
  ],
  "direct": {
    "orders": [
      {"id": 9, "order_no": "ORD-...", "status": "confirmed",
       "documents": [{"doc_no": "PL-...", "doc_type": "pl"}]}
    ],
    "documents": [
      {"id": 2, "doc_no": "CI-202609-0001", "doc_type": "ci", "status": "issued"}
    ]
  }
}
```

**为什么必须有 `direct`**：手动新建与导入的历史单据**没有报价这一环**（见 §1.6），
如果不单独返回它们，客户页就会"少东西" —— 与"支持导入已有数据 / 要能查到历史"直接冲突。
`direct` = "直接归属客户的订单与单证"，前端**固定渲染**，一条都不丢。

- 排序：报价按 `created_at DESC`；报价下的订单升序（业务时间线）；单证按 `created_at`
- 分页：报价分页（`page`/`page_size`，默认 20），其下的订单与单证随报价整体返回（避免前端 N+1）
- 可见性：先走客户可见性校验（复用 `_get_customer_or_404`），不可见 → 404 `CUSTOMER_NOT_FOUND`
- **不按状态过滤**：草稿/已发出/已接受/已确认/作废全部返回，用 `status` 让前端区分

## 4. 展示效果（前端设计）

客户详情页新增「往来记录」区：

```
Tim Trading                                           3 报价 · 2 订单 · 6 单证
──────────────────────────────────────────────────────────────────────────
▾ QUO-202609-0004   已接受     USD 12,300      2026-09-27
  │  单证  [报价单] QUO-202609-0004
  └▾ ORD-202609-0001  已确认    USD 12,300      2026-09-28
        单证  [形式发票] PI-202609-0002   [商业发票] CI-202609-0001
              [装箱单] PL-202609-0003     [提单] BL-202609-0004
▾ QUO-202609-0003   已发出     USD 8,000       2026-09-27
  │  单证  [报价单] QUO-202609-0003
  └  （未成单）
▸ QUO-202609-0002   草稿       —               2026-09-26
    单证  [报价单] （尚未生成）
▸ 未关联到报价的历史数据（1 订单 · 2 单证）
```

设计要点：

| 点 | 做法 |
|---|---|
| 层级 | 客户 → 报价 → 订单，单证以 **chip** 贴在所属节点下（缩进 + 竖线表达包含关系） |
| **单证不分家** | 报价单与 PI/CI/PL/BL **同一套 chip 组件、同一处展示**，只用图标/颜色区分 `doc_type`，绝不放两个模块 |
| 状态 | 复用现有 status 枚举配色（草稿灰 / 已发出蓝 / 已接受绿 / 已确认绿 / 作废红划线） |
| 默认展开 | 含订单的报价默认展开（业务最关心）；纯草稿折叠 |
| 计数 | 标题右侧汇总 counts，点击可筛选 |
| 未关联 | 折叠区，避免历史脏数据污染主视图，但**能查到** |
| 空态 | 该客户还没有任何报价/订单/单证时，显示"新建报价"引导（报价工位是入口） |

## 5. 配套改动（让新数据天然带包含关系）

1. **报价转订单时写 `orders.quote_id`**（这是包含关系的来源，必须落库）
2. **生成报价单时写 `trade_docs.quote_id` + `doc_type='quotation'`**
3. **生成 PI/CI/PL/BL 时写 `trade_docs.order_id`**
4. **三张单据表新建时都必须选已有业务客户**（`customer_id` 必填、必须属本团队）
5. 历史回填：`trade_docs.customer_id` 按客户名尽力回填（迁移 `009`）；
   能按 `doc_no`/`order_no` 推断归属的尽量回填 `quote_id`/`order_id`，推不出的留在 `direct`（直接挂客户）分组

## 7. 两套关联机制：列 vs 链接表（重要，别踩坑）

仓库里**同时存在**两种表达"报价 ↔ 订单 / 单证"关系的方式：

| 机制 | 位置 | 现状 |
|---|---|---|
| **列** | `orders.quote_id`、`trade_docs.quote_id` / `order_id` | 本次新增；**归属的唯一口径**（1:N、可用 CHECK 约束兜底、查询免 JOIN） |
| **链接表** | `order_quote_refs`、`trade_doc_quote_refs`、`trade_doc_order_refs` | **先有、在用、有真实数据**：`trade_doc_quote_refs` 3 行（单证 2/3/4 由报价 2/3/4 `generated_from`）；`app/api/orders.py`、`app/api/trade_docs.py`、worker 同款路径都在写 |

**坑**：读侧若只看列，既有写入路径产生的单据会被错判成"只归属客户"落进 `direct` ——
表现为**客户页看不到它挂在哪个报价下**（静默少显示，界面上最难发现）。

**当前做法（过渡期）**：读侧 **列优先、链接表兜底**。
- dev：`app/api/customer_records.py` 的 `_resolve_parents()`
- worker：`ws_customer_records.py` 的 `_resolve_parents()`

**目标状态**：
1. 写入侧统一到**列**（`orders.quote_id`、`trade_docs.quote_id`/`order_id`）
2. 链接表**保留为关系审计**（`ref_type` 如 `generated_from` 表示"由谁生成"，语义比"归属"更细，可多条）
3. 历史数据从链接表**回填到列**后，兜底逻辑可退化为"仅审计查询"

在写入侧统一 + 历史回填完成之前，**不要删除兜底逻辑**，否则并存期的数据会静默消失。

### 单证归属的最终口径（与实现对齐）

**不按 `doc_type` 决定挂谁**，而是"有哪个父对象就挂哪个，二选一"：

| 单证来源 | `quote_id` | `order_id` | 树里位置 |
|---|---|---|---|
| 生成报价时自动产出（报价单） | 报价 | NULL | 该报价下 |
| 由报价直接生成（PI/CI/PL/BL） | 报价 | NULL | **该报价下**（不是 direct） |
| 由订单生成 | NULL | 订单 | 该订单下 |
| 手动新建 / 导入 | 可选 | 可选 | 有则挂上，都没有 → 客户页 `direct` 分组 |

**证据**：`trade_doc_quote_refs` 的真实数据是 `CI→报价2`、`PI→报价3`、`PI→报价4` ——
说明"从报价直接出 PI/CI"是本系统的既有业务形态，按类型硬绑定会把这些单证错误地推进 `direct`。

### 装配逻辑只有一份
树装配在共享内核 `kaas_common/workstation/customer_records.py`；dev 与 worker 只负责
"把三类行查出来 + 解析归属"，**装配不各写一份**（否则两端迟早出现归属口径漂移）。
