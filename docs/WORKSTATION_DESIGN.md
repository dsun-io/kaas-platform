# KaaS 平台工作站总体设计

> **KaaS (Knowledge as a Service)** —— 为传统制造业提供 AI 岗位能力托管。
> 平台以「工作站 (Workstation)」为最小交付单元：每个工作站是一个垂直业务域，
> 既能**独立运行**，又能通过统一的数据层与其它工作站**上下游联通**。
>
> 本文档定义工作站体系结构、数据连通契约与演进路线，是后续所有工位开发的**不变参照**。

---

## 1. 术语定义

| 术语 | 含义 |
|------|------|
| **工作站 (Workstation)** | 一个面向特定业务目标的 AI 能力单元，含前端页面 + 后端 API + 数据表 |
| **工位** | 与「工作站」同义，口语表达 |
| **上下游联通** | 工作站间通过共享数据库键引用、事件流或 API 调用形成数据链路 |
| **独立运行** | 单个工作站不依赖其它工作站即可交付完整价值（自洽的表 + 接口 + 页面） |
| **口子 (Schema 预留)** | 在数据库中预先建立跨工位引用的外键/关联表，使后续工位无需破坏性变更即可接入 |
| **KaaS 数据链** | 平台统一的领域数据骨架：`客户 → 产品(SKU) → 报价 → 订单 → 票据 → 货运` |

### 2.0 命名口径（2026-09-22 变更）

### 2.0.1 情报体系（三工位）

情报体系由三个工位组成，层次为「宏观 → 微观 → 源头」：

```
情报体系
├── 进出口情报             （宏观）海关/贸易数据、货运记录、竞争格局
├── 市场调研               （微观）从地图源挑选数据并深化：规格/价格/能否提供
└── 地图源客户信息获取     （源头）Google Places 抓取店铺 + 爬官网提取产品
```

**地图源客户信息获取是双重身份**：属于情报体系，同时是主业务链起点。
前端菜单归入「情报体系」，产出（线索池）被业务链消费。

### 2.0.2 分工原则：脚本为主，AI 为辅

两个数据加工工位共用同一条原则 —— **能算的用脚本，难量化的才用 AI**：

| 环节 | 手段 | 理由 |
|------|------|------|
| 店铺信息（名称/地址/电话/评分/类型/link） | Google Places API | 权威、结构化 |
| 产品信息（图片/当地叫法/规格） | **爬官网 + 正则提取** | Google Places 看不到产品 |
| 规格结构化（尺寸/材质） | **脚本正则**（`_template_spec_extract`） | 确定性、可复现、零成本 |
| 中文对照（当地叫法→中文） | AI 翻译（`product_translate`） | 难量化，AI 未启用则留空待人工填写 |
| 能否提供 | **用户手动判定** | 商业判断，禁止 AI 推断 |
| 产品品类归类 | 用户选择 | 枚举约束，避免漂移 |

> AI 未绑定时的降级路径已定义：规格仍由脚本产出，中文对照留空，
> 系统不阻塞、不臆测、不写错数据。

## 3. 核心设计原则

### 3.1 单工位自洽 (Independent)
每个工作站拥有自己的表（`{domain}_*` 前缀）、API（`/api/v1/{domain}/*`）与前端路由（`/{domain}`）。
- 商情雷达：`intel_*` 表 + `/api/v1/intel/*` + `/intel`
- 报价工位：`quote_*` 表 + `/api/v1/quote-orders/*` + `/quote-orders`
- 订单工位：`orders_*` 表 + `/api/v1/orders/*` + `/orders`
- 票据工位：`trade_docs_*` 表 + `/api/v1/trade-docs/*` + `/trade-docs`

任何工位可单独上线、单独灰度、单独回滚，不阻塞其它工位。

### 3.2 数据连通 (Connected)
跨工位不共享表，通过**稳定业务键**引用：
- 实体主键 `id`（全局自增，跨库唯一）
- 业务编码 `order_no` / `quote_no` / `doc_no`（人类可读，幂等键）
- 租户键 `tenant_id`（多租户隔离不变量）

上游写入、下游读取时，用外键或关联表显式记录引用关系（见 §5）。

### 3.3 松耦合接口 (Loose Coupling)
- **同步联通**：下游工位直接读取上游工位的表（只读视图/查询），通过 `*_refs` 关联表显式建模
- **异步联通**（预留）：事件表 `domain_events`，工位发布领域事件，下游订阅消费
- **禁止**：跨工位直接 UPDATE/DELETE 对方数据；写操作必须经本工位 API

### 3.4 渐进式交付 (Progressive)
先建「口子」（表结构 + 只读引用），后填「血肉」（业务逻辑）。每个工位 MVP 只需：
1. 建表（含跨工位引用键）
2. 实现本工位 CRUD
3. 实现读取上游数据的只读接口

## 5. 跨工位数据连通契约

> 以下关联键在数据库迁移 `20260919_workstation_links` 中已建立，是所有工位的**接入点**。

### 5.1 关联表总览

| 关联表 | 上游 → 下游 | 语义 |
|--------|------------|------|
| `quote_order_shipment_refs` | intel → quote_orders | 报价单依据哪些货运记录生成（买家/产品信号溯源） |
| `order_quote_refs` | quote_orders → orders | 销售订单由哪些报价单转化而来 |
| `order_shipment_refs` | orders → intel | 订单关联的实际出运记录（商情雷达回写） |
| `trade_doc_order_refs` | orders → trade_docs | 票据由哪些订单生成 |
| `order_shipment_refs` | intel → orders | 订单引用货运记录作为物流依据（双向） |

### 5.2 引用键约定

每个关联表遵循同一模式：
```sql
id          BIGSERIAL PRIMARY KEY
tenant_id   TEXT NOT NULL                -- 多租户隔离
{domain}_id BIGINT NOT NULL              -- 上游记录 id
ref_type    TEXT NOT NULL                -- 引用语义标签 (如 'buyer_signal', 'converted_from', 'actual_shipment')
ref_target_id BIGINT                     -- 下游记录 id
ref_no      TEXT                         -- 冗余业务编码 (人类可读，如订单号)
created_at  TIMESTAMPTZ DEFAULT now()
UNIQUE(tenant_id, {domain}_id, ref_type, ref_target_id)   -- 幂等
```

### 5.3 未来扩展位
- 在 `quote_orders` / `orders` / `trade_docs` 主表上预留 `linked_{domain}_id` 冗余外键，
  便于高频查询场景下避免 JOIN 关联表。
- 关联表 `ref_type` 用开放字符串，新业务语义无需 ALTER TABLE 即可接入。

### 5.4 订阅化改造（Phase 6 前置设计）

> 工位独立不仅是逻辑分层，更是**商业边界**。客户可单独订阅任一工位，
> 也可订阅场景包（多工位组合）。不订阅的工位代码不执行、接口不暴露、数据不写入。

**订阅模型**：

```sql
-- 订阅主表
subscriptions (
  id BIGSERIAL PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  plan_code TEXT NOT NULL,          -- 'intel' / 'customers' / 'market' / 'quote' / 'orders' / 'docs'
  plan_type TEXT NOT NULL,          -- 'single' / 'bundle' / 'enterprise'
  bundle_code TEXT,                 -- 场景包编码, 如 'export_starter'
  status TEXT NOT NULL,             -- 'active' / 'expired' / 'cancelled'
  started_at TIMESTAMPTZ,
  expires_at TIMESTAMPTZ,
  UNIQUE(tenant_id, plan_code, status)   -- 同一工位同时只有一条有效订阅
)

-- 场景包定义（哪几个工位组合成一个包）
subscription_bundles (
  id BIGSERIAL PRIMARY KEY,
  bundle_code TEXT UNIQUE NOT NULL,  -- 'export_starter' / 'export_pro' / 'full_chain'
  name TEXT NOT NULL,
  description TEXT,
  plan_codes TEXT[] NOT NULL,        -- ['customers','market','quote']
  price_cny NUMERIC,
  is_active BOOLEAN DEFAULT true
)
```

**订阅场景包示例**：

| 场景包 | 包含工位 | 目标客户 |
|--------|---------|---------|
| `export_starter` | customers + market + quote | 刚起步外贸企业 |
| `export_pro` | customers + market + quote + orders + docs | 成熟外贸企业 |
| `full_chain` | 全工位 | 全链路数字化 |

### 5.4.1 实际落地的订阅编码（2026-09-22 口径）

> **本期不激活订阅治理**：`tenant_subscriptions` 保持 `default = full_chain`，
> 前端不暴露订阅入口。编码已在 `chain.py` `SUB_CODES` 登记，填行即生效。

| 编码 | 包含 | 工位 key |
|------|------|---------|
| `intel_trade_starter` | 进出口情报 | `intel` |
| `intel_research_starter` | 市场调研 | `research` |
| `intel_full` | 情报体系三工位 | `intel` + `research` + `leadgen` |
| `leadgen_starter` | 地图源客户信息获取 + 线索池 | `leadgen` |
| `outreach_starter` | 客户触达（含产品手册附件） | `outreach` |
| `full_chain` | 全工位 | 全部 |

**生效方式**（未订阅 → 404 `SUBSCRIPTION_REQUIRED`）：

```python
SUB_CODES = {
    "leadgen":  ["leadgen_starter", "full_chain"],
    "outreach": ["outreach_starter", "full_chain"],
    "intel":    ["intel_trade_starter", "intel_full", "full_chain"],
    "research": ["intel_research_starter", "intel_full", "full_chain"],
}
```

> 历史遗留：`leadgen_pro` / `outreach_pro` 为预留档位，保留在 `SUB_CODES` 中向后兼容。

**订阅生效控制三层防线**：

```
① API 层：中间件检查 subscription，未订阅 → 404（不是 403，不暴露存在性）
② 前端层：侧边栏只渲染已订阅工位入口，路由未订阅 → 重定向到订阅页
③ 数据层：跨工位写入前检查订阅，未订阅工位不产生任何写入
```

**订阅状态判定规则**：

| 场景 | 判定 |
|------|------|
| 单工位订阅 | `subscriptions.plan_code = X AND status = 'active'` |
| 场景包订阅 | `subscription_bundles.plan_codes @> ARRAY[X] AND 对应 subscription.status = 'active'` |
| 企业版 | 所有工位默认生效，跳过单工位检查 |

**降级行为（关键体验约束）**：

| 未订阅工位被触发 | 行为 |
|----------------|------|
| 前端路由访问 | 显示"该工位未订阅"引导页，提供订阅入口 |
| API 直接调用 | 返回 `{"error": "workstation_not_subscribed", "plan_code": "X"}`，HTTP 404 |
| 下游工位依赖未订阅上游 | 显示降级提示，不阻断当前工位已订阅功能 |

**新增工位接入订阅的检查清单**：

- [ ] `subscription_bundles.plan_codes` 数组加入新工位编码
- [ ] 该工位所有 API 路由加订阅中间件
- [ ] 前端侧边栏入口加订阅条件渲染
- [ ] 跨工位写入点加订阅检查（防绕过）
- [ ] 未订阅时前端展示引导页而非空白

## 6. 各工位 Schema 概要

### 6.1 智能报价工位 `quote_orders`（预留口子 + 报价引擎 V2 规划）

承载从商情雷达信号 / 询盘意向 → 结构化报价单的全链路。当前已建表，业务逻辑按下方报价引擎设计填充。

**核心表**：
- `quote_orders` — 报价单头（客户、币种、有效期、状态机）
- `quote_order_items` — 报价单行项（SKU 引用、数量、单价、行金额）
- `quote_freight_charges` — 运费记录（海运费、本地费、币种、供应商）
- `quote_raw_material_refs` — 原材料参考价历史（来源：manual / auto / historical）
- 关联：`quote_order_shipment_refs`（上游=商情雷达货运记录）

**报价引擎 V2 核心逻辑**：

```
选择产品 + 输入规格
        │
        ▼ ① 自动计算体积和重量
   ┌─────────────────────────────────────┐
   │ 体积 = 数量 × 单件体积（或包装尺寸推算）│
   │ 重量 = 数量 × 单件重量（SKU 命中则回填）│
   └─────────────────────────────────────┘
        │
        ▼ ② 原材料成本（三选一，用户主动选择）
   ┌────────────────────────────────────────────────────┐
   │ A. 手动输入成本价                                   │
   │ B. 不输入（跳过成本计算，仅按历史价/SKU价）          │
   │ C. 应用系统参考价（系统计算，展示但需用户确认后才用）│
   └────────────────────────────────────────────────────┘
        │
        ▼ ③ 成本加成报价
   ┌──────────────────────────────────────────────────────┐
   │ ⚠ 本行公式已被 §6.1.1 的完整税链取代（2026-09-25）    │
   │ 旧式：(成本 + 加工费) × (1+税率) × (1+利润率)        │
   │ 问题：把增值税当成本加成因子，且忽略出口退税让利       │
   └──────────────────────────────────────────────────────┘
        │
        ▼ ④ 国际贸易条款价（用户选择条款 + 录入/读取运费）
   ┌─────────────────────────────────────────────────────┐
   │ EXW  = 出厂价（不含运费）                            │
   │ FOB  = EXW + 本地费（内陆运费 + 港杂费 + 报关费）    │
   │ CFR  = FOB + 海运费                                 │
   │ CIF  = CFR + 保险费                                 │
   └─────────────────────────────────────────────────────┘
        │
        ▼ ⑤ 输出三档报价方案（已有 V2 逻辑）
   逼单方案(low) / 让利方案(standard) / 优选方案(high)
```

### 6.1.1 出口报价引擎（已实现，2026-09-25）

上述 ③ 的成本加成式在实际出口业务里不成立：增值税是**价外税**，出口还涉及
**进项退税与让利**。已按正确的税链实现为独立服务层，与产品解耦：

```
backend/orchestrator/app/services/export_quote/
├── pricing.py    价链：成本 → 进项税 → 退税让利 → 印花税 → 销项税 → 报价
├── rates.py      税务档案（版本化）+ HS 退税率查询（可插拔 Provider）
├── terms.py      贸易术语阶梯 EXW→FCA→FOB→CFR→CIF
├── engine.py     组装：规格展开 → 派生 → 价链 → 术语 → 指标 → 列投影
├── verify.py     三遍交叉核验 + 关系式 + 阶梯 + 档案自检
├── report.py     xlsx / csv / dict（内部与客户双投影）
├── products/     产品知识（牛栏网），引擎本身不认识任何产品
└── rate_sets/    税务档案 yaml（带生效日期）
```

**正确价链**（每一条都由 `verify.py` 的关系式锁定）：

```
含税采购价              = 税前成本 ÷ (1 − 进项票税点)
进项税额                = 含税采购价 − 税前成本
可退进项增值税税额      = 进项税额 × (出口退税率 ÷ 征税率)
不可退进项税额          = 进项税额 − 可退进项增值税税额      ← 真成本
让利额                  = 可退进项增值税税额 × 让利比例
自留可退税额            = 可退进项增值税税额 − 让利额        ← 风险对冲
印花税                  = 计税基数 × 印花税率（默认基数 = 加工利润）
不含税售价              = 含税采购价 + 加工利润 − 让利额 + 印花税
销项税额                = 不含税售价 × 销项税率              ← 基数是售价，不是成本
含税售价                = 不含税售价 + 销项税额
最终客户价              = 含税售价 + Σ 贸易术语附加费用
```

等价式（同样作为不变量校验）：
`不含税售价 = 税前成本 + 加工利润 + 不可退进项税额 + 自留可退税额 + 印花税`

**关键设计约束**：

| 约束 | 做法 |
|------|------|
| 不硬编码产品/金额/税率 | 全部走配置；牛栏网专有逻辑只在 `products/field_fence.py` |
| 国家调税不炸（印花税 5%→6%、增值税 13%→12%） | 税率集中在**带生效日期**的档案；政策变化**新增**档案，不改旧档案 ⇒ 历史报价可逐分复现 |
| 退税率不靠猜 | 按 HS 编码查；查不到**明确报错**（`RebateRateNotFound`）。没有免鉴权的公开官方退税率 API，故 Provider 可插拔（HTTP → 本地档案库），查不到就交人工确认 |
| 对外不暴露成本利润率 | 列上标 `internal`，生成时切分两张投影；`/calculate` 只给客户视图，内部视图要租户管理员 |
| 单价 × 数量 = 总价 | 作为产品不变量逐行逐订单校验，且"每米价 × 总米数"同时成立 |
| 报错优于静默兜底 | 汇率 ≤ 0、费用既无 value 也无 source 都直接报错 —— 静默按 0/1 取值会让整张报价单偏低 |

### 6.1.2 计算逻辑随产品一起交付

光有输入属性不够 —— 业务要能回答「波弯款到底怎么加的」「29.9 立方怎么来的」，
不能每次都回头问开发。所以计算逻辑与口径说明跟产品定义放在一起，并可被接口读出：

```python
# 每条公式都带中文名、单位、落定小数位与**业务口径说明**
FormulaSpec("wave_add_kg",
            "wave_factor * wave_add_per_100m * roll_len_m / 100", ...,
            label="波弯增重(kg)", unit="kg",
            note="波弯款按每 100 米增重 3kg 折算：增重 = wave_factor × 3 × 卷长 ÷ 100。"
                 "无波款 wave_factor=0 故增重为 0；100 米卷 +3kg，50 米卷只 +1.5kg。")
```

**牛栏网计算逻辑一览**（`GET /products/field_fence/formulas` 返回全量）：

| 量 | 口径 |
|---|---|
| 单卷基础净重 | `0.00617 × L × [2·d边² + (n−2)·d横² + d竖² × (w + (n−1)×50) / s]` |
| 单卷边丝重 | `0.01234 × L × d边²`（两侧合计，系数是 0.00617 的两倍） |
| **波弯增重** | `wave_factor × 3 × L ÷ 100` → 100 米卷 +3kg、50 米卷 +1.5kg |
| 单卷净重 | `基础净重 + 波弯增重`（4 位小数落定） |
| **单卷净体积** | `π/4 × 卷径² × 网高`（按**实际圆柱体**，即 π × (卷径/2)² × 网高） |
| **单卷长方体体积** | `卷径² × 网高`（按**外接方柱**，用于堆码与报运价） |
| 长方体总体积 | `单卷长方体体积 × 卷数`（**尚未扣减**） |
| **实际占用体积** | `长方体总体积 − 2.5 m³`（2~3 取中位数，**每单只扣一次**） |
| 卷数 | `订单总长度 ÷ 每卷长度`（全丝2.5 每卷 50 米、其余 100 米） |
| 单卷售价 / 每米价 / 外币价 | `单价 × 单卷净重` → `÷ 卷长` → `÷ 汇率` |

**体积为什么是两个口径**：单卷净体积回答「这批钢材本身体积多大」（圆柱体）；
单卷长方体体积回答「这些卷怎么占地方」（外接方柱）。**对外报运价/报关用实际占用体积**，
它基于长方体口径扣减 —— 圆柱体只是钢材本身。两者差约 π/4 ≈ 78.5%，
混用会算错运价，所以分开命名、各有一列。

**卷径**：默认值随丝径方案联动（100 米卷 30cm、50 米卷 25cm），
可按实际装箱用 `variant_overrides` 覆盖，不必改产品定义。

`POST /products/{key}/explain` 给一组规格取值后**逐步代入**，把每个中间量算出来，
用于「这个数字怎么来的」当场自证。该接口只讲数量口径，不含成本与利润，
因此普通登录用户即可调用；价格类指标会显式列出并提示改用 `/calculate`。

### 6.1.3 与规格体系的属性对齐

平台另有一套规格体系（Category → Attribute → SKU → Price，见 `shared/contracts/spec-system.ts`）。
牛栏网的属性已按报价口径整理进该体系（迁移 `202609250001_niulanwang_product_attributes`）：

- **SKU 轴**恰好 5 个，组合数 48：丝径方案 × 网高 × 竖丝间距 × 镀锌量 × 工艺 = 3×2×2×2×2
- **描述性属性**（记录但不参与 SKU 编码）：网孔分布、表面处理、包装、横丝数、
  边丝径／内横丝径／竖丝径、卷长、卷径、网孔规格、丝径、网宽
- **派生量属性**（`source='derived'`，只读）：单卷基础净重、单卷边丝重、波弯增重、
  单卷净重、单卷净体积、卷数、订单总净重、长方体总体积、实际占用体积、
  单卷售价、单价、单卷美元售价

两条建模原则（踩过坑，写在迁移注释里）：

1. **只有真正会变的量才做 SKU 轴**。网孔分布按品种固定为「拧编型上疏下密」，
   若当作变体轴会虚增成 3×3×2×2×2×2 = 144 个组合。
2. **由其它轴决定的量不要做轴**。卷长由丝径方案决定（全丝2.5 → 50m/卷），
   若留作 SKU 轴会产生「全丝2.5 + 100m/卷」这类不存在的组合。

同时补了两个缺失的基础单位：`units.cbm`（体积，平台既有命名）与
`price_units.usd_per_roll`（USD/卷）。

### 6.1.4 表格批量导入（一键算完整张表）

**要解决的问题**：报价时逐个输入参数太慢。客户常直接甩来一张表，
或我们自己导出的报价表要改汇率重算。都需要一次性批量算完。

#### 引擎侧：显式规格行模式

原先 `build()` 只会把产品的规格轴展开成**笛卡尔积**（牛栏网 48 行），
表达不了「客户只问这 12 个组合」。所以给 `QuoteRequest` 加了 `spec_rows`：

```python
QuoteRequest(spec_rows=[
    {"wire": "全丝2.0", "height_m": 1.2, "mesh_mm": 100,
     "coating": "普锌40g/㎡", "wave": "无波款"},
    ...
])
```

- 给了 `spec_rows` → **只算给的那些行**，不再展开全组合
- 变体包给**取值名**即可，引擎自动带出该方案的全部属性
  （`wire="全丝2.0"` → de/dm/dv/roll_len_m/roll_dia_m 一次全定）
- 也认稳定 code（`wire_code="all_wire_20"`），与 DB 的 `value_code` 同一套标识
- **一行坏不拖垮整批**：坏行跳过并回报「第几行/哪一列/什么值/期望什么」，好行照算

#### 单位跟表头走，不靠猜

这是最容易错的地方：`竖丝间距(cm)` 填 `10` 是 100mm，`mesh_mm` 填 `100` 也是 100mm。
若按「数字多大就猜什么单位」，10 会被当成 10mm —— **整批差十倍**。

所以导入器解析表头时把单位一起取出来，按单位换算：

| 表头 | 值 | 归一为 |
|---|---|---|
| `竖丝间距(cm)` | 10 | `mesh_mm = 100` |
| `mesh_mm` | 100 | `mesh_mm = 100`（不换算） |
| `Net Height (m)` | 1.2 | `height_m = 1.2` |
| `卷长(m/卷)` | 100 | `roll_len_m = 100`（括号里带中文量词也认） |
| `网高`（无单位） | 1.2 | 按业务惯例当 m |

引擎本身**不做跨单位换算**（只容忍同单位后缀如 `1.2m`），
换算责任只在导入器一处，避免两边都换算造成双重折算。

#### 认得出我们自己导出的表

表头别名表覆盖三种写法，所以「上传上次导出的 xlsx → 一键重算」开箱可用：

- 导出文件的中文列名：`网高(m)` / `竖丝间距(cm)` / `丝径方案` / `镀锌量` / `工艺` / `卷长(m/卷)` / `卷径(cm)`
- 英文：`Net Height (m)` / `Vertical Wire Spacing (cm)` / `Zinc Coating` / `Wave Bend`
- 内部字段名：`height_m` / `mesh_mm` / `wire` / `coating` / `wave`
- 取值也容错：`全丝2.0` / `all_wire_20` / `2.0x2.0` 都指同一个方案

导出文件里那些计算列（净重、售价、税额…）会被归入 `ignored_columns`，
不算错误 —— 只取规格列重算。

**列名识别只有一处**：解析上传的表与生成下载的模板共用同一个
`_resolve_column()`。两处各写一套必然走岔 —— 一边认得、另一边不认得，
用户下载的模板填好却传不上去，而且这种错不会报错，只会静默丢列。

#### 模板：从系统直接下载，不用手工造

模板**不是手写的一套表头**，而是从产品声明里反推出来的：拿产品自己的输出列
（也就是导出报价表用的那些列名）逐列去问解析器「这个表头你认得吗」，认得就写进模板。
于是三边永远一致：

```
模板表头 ≡ 导出的报价表表头 ≡ 上传时解析器认得的表头
```

将来产品加列或改列名，模板与解析一起跟着走 —— 不会出现「代码改了、模板没改，
下载下来填好却传不上去」。**这条不是空话**：实现前模板只按变体包生成，
漏掉了「网高(m)」「竖丝间距(cm)」两个规格轴，下载的模板根本填不出规格；
现在有一条反向断言盯着这件事（`test_no_recognised_export_column_is_dropped`）。

**Excel 模板**（默认，给人填）含三个工作表：

| 工作表 | 内容 | 会不会被上传计算 |
|--------|------|------------------|
| 规格表 | 表头 + 可选值**下拉框** + 冻结首行 | **只认这个**（解析器读第一个工作表） |
| 示例 | 3 行填好的示例，可复制到「规格表」 | 不会 |
| 填写说明 | 逐列说明：必填与否、单位、可选值、留空规则、容错规则 | 不会 |

示例刻意放在单独的表里：放在「规格表」下方会被连带算进去，
用户加了行再上传就凭空多出几行重量与金额。

示例值按**表头单位**给 —— 内部 100mm 的竖丝间距，在 `竖丝间距(cm)` 列里写 `10`。
单位认错会整批差十倍，所以这里宁可多绕一道换算。规格轴的数字写成**数值**而不是
数字串（文本会被 Excel 标绿三角，用户后续排序/公式都别扭）。

候选值太长（内联下拉串超过 240 字符）时自动改用隐藏的 `lists` 表 + 区域引用，
不会因为某个产品的取值名太长就生不出模板。

**CSV 模板**（给脚本化生成用）：默认只出表头，带 BOM。

#### 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/import/template` | 下载模板；`format=xlsx`（默认，带下拉与说明表）或 `csv`；`examples=N` 控示例行数 |
| GET | `/products/{key}/import-template` | 只回报模板**长什么样**：列名、必填、单位、可选值、下载链接（先讲清再下载） |
| POST | `/import/preview` | 只解析不计算：回报列映射、可用行、逐行问题 |
| POST | `/import/calculate` | 解析 + 一次性批量计算（`view=customer\|internal`） |

模板响应另带两个响应头：`X-Template-Columns`（列名 JSON）、
`X-Template-Spec`（带 `include_spec=true` 时的完整列定义），
让前端在拿到文件的同时就能渲染「该填哪些列」，不必先解一次文件；
跨域时用 `Access-Control-Expose-Headers` 放行。
**头值一律 ASCII 转义** —— HTTP 头只能 latin-1，中文直接塞进去会让请求 500。

`/calculate` 与 `/calculate-internal` 也接受直接传 `spec_rows`，
便于「先预览→人工改→再算」的两步流程与 API 自动化。

**容错与限额**：单文件上限 2MB、单表上限 2000 数据行；重复行自动跳过并提示；
空文件/只有表头/无规格列/`.xls` 老格式都会给出明确原因而不是 500。
内部视图沿用与 `/calculate-internal` 相同的管理员权限要求。

#### 前端流程

```
报价工位 ·「批量导入」页签
   ①  选产品 → 看到该产品模板的列清单（必填列标 *）
       点「下载 Excel 模板」/「CSV（只有表头）」
   ②  填好表 → 选择文件（本地先查格式与大小，明显不对就不占用一次往返）
       可填订单量 / 汇率 / 税务档案 / 进项票税点 / 让利比例 / 报价日期
   ③  先预览         → 列映射、可用 38 行 / 3 行有问题、逐条问题清单
   ④  批量计算        → 摘要（行数、总净重、总售价、外币总价）+ 结果表
   ⑤  导出 CSV       → 带 BOM，中文列名在 Excel 里不乱码
```

前端与后端的分工：**报价的真值只在引擎里有一份，前端不重算**。
摘要里的总净重/总价直接读结果里的合计，避免前后端各算一遍而对不上。
前端只负责「该拦的先拦」（文件格式/大小）、「该说的说清」（列清单与问题清单）。

前端纯逻辑抽在 `frontend/src/lib/export-quote/import-file.ts`：
下载地址拼接、multipart 表单、预检、问题分组、摘要、CSV 导出、文件名解析。

`application/json`，而 axios 见到 JSON 默认头会把 `FormData` 转成 JSON，
**文件就传丢了**；这是最容易踩且最难查的一个坑，所以单独写了一条测试盯着。

契约见 `shared/contracts/export-quote.ts` 的

**原材料参考价计算规则**：

| 来源 | 规则 | 可信度权重 |
|------|------|-----------|
| 用户手动输入 | 直接采用 | 最高（显式指定） |
| 系统历史均值 | 近 N 次报价中实际采用成本的加权均值（时间越近权重越高） | 高 |
| SKU 关联参考价 | 该 SKU 最近一次成功报价的原材料成本 | 中 |
| 无历史 | 提示用户手动输入，不自动填充 | — |

**关键设计约束**：
- 系统**永不自动应用**参考价——必须用户主动选择"应用参考价"才生效
- 参考价**只作建议展示**，与应用值分开存储（`suggested_cost` vs `applied_cost`）
- 对外展示不得暴露成本利润率（已有铁律）

**运费数据来源**：
- 手动输入（货代报价单拍照/邮件）
- 市场对照工位港口情报推荐（Phase 6）
- 历史运费均值（同港口 + 同货类）

- `trade_doc_order_refs`（上游=订单）

### 6.4 客户管理工位 `customers`（规划中，统一底座）

承载客户全生命周期：从询盘录入 → 客户建档 → 阶段跟踪 → 成交转化。

核心表（规划）：
- `customers` — 客户主档（公司名、联系人、国家、地址、默认港口、信用等级）
- `customer_contacts` — 联系人多条（姓名、职位、电话、email、whatsapp、微信）
- `customer_inquiries` — **询盘记录**（从询盘入口直接录入，自动关联客户）
  - 询盘渠道（email/whatsapp/阿里/展会/其他）
  - 意向产品（品类 + 品名原文 + 数量 + 用途）
  - 询盘状态：`询盘中 / 已报价 / 已成交 / 已流失`（**单据阶段**，与客户阶段是两层）
  - 成交后自动生成 `orders` 记录（订单状态是订单自己的阶段）
- `customer_stage_log` — **客户阶段**变更历史（只记手动切换活跃/沉寂）

**客户阶段（2026-10-18 用户口径，已实现）**

客户阶段只有三种：`active 活跃` / `inactive 沉寂` / `ordered 已下单`。

- `active` / `inactive` 是**手动状态**（存在 `customers.stage`），由用户在客户页手动切换；
  「沉寂」= 客户关系关闭。
- `ordered` 是**读时推导值**，不落库：名下存在**开启中的订单**
  （`pending / confirmed / producing / shipped`，即未完成且未取消）时显示「已下单」；
  订单一完成/取消，自动回到活跃或沉寂。
- **不再把询盘/报价/订单的状态映射成客户阶段**：`lead→inquiry→quoted→won→lost`
  属于单据阶段，`orders.status` 才是每张订单的源头；「流失」属于订单阶段，
  客户阶段里没有 `lost`。
- 不再按 30/90 天无活动自动改客户阶段（「沉寂先手动切换」）。

**客户 CRUD（2026-10-18 补齐）**

- 编辑：`PATCH /customers/{id}` 改档案（公司名/国家/地址/港口/信用等级/备注），
  联系人走各自的 `PATCH/DELETE /customers/{id}/contacts/{contact_id}`。
- 删除：`DELETE /customers/{id}` **软删除**（列表隐藏、历史单据保留引用）；
  名下有开启中的订单时返回 **409 `OPEN_ORDERS_EXIST`**（附订单清单），需先关闭订单。
- 新建/列表/详情/编辑的响应都带 `stage`（展示值）与 `manual_stage`（手动值）。

**询盘入口流程**：
```
收到询盘（邮件/WhatsApp/阿里/展会）
        │
        ▼ 录入询盘信息
客户是否存在？── 否 ──► 自动新建客户档案 + 首条询盘记录
        │
        是 ──► 关联已有客户，新增询盘记录
        │
        ▼ 匹配市场对照工位
   建议规格 / 品名对照 / 最近港口
        │
        ▼ 业务员跟进，更新询盘状态
   询盘中 → 已报价 → 已成交 / 已流失
        │
        ▼ 状态 = 已成交
   自动生成订单（转入订单工位）
   客户阶段 = 已成交
```

### 6.5 产品市场对照工位 `market`（规划中）

回答"什么地区卖什么产品、常用什么规格、当地人管这个产品叫什么"。支持按**地区**、**产品名（中英文/各语种）**、**用途**查询。

核心表（规划）：
- `market_region_products` — 地区×产品对照（需求等级、认证要求、执行标准、季节规律）
- `market_region_product_specs` — 常见规格参数对照（spec_key/spec_value/unit + 频率排序 + SKU 挂接）
- `market_product_name_mappings` — 中外品名对照（region + lang → 当地品名、别名 JSONB、HS 编码、是否核实）
- `market_product_usages` — 用途分类（fence / construction / agriculture / security…，与品名映射关联）
- `market_ports` — 港口情报库（**静态主档 + 动态运营数据两层**）

| 层 | 字段 | 说明 |
|----|------|------|
| **静态主档**<br>（地理位置、物理条件，确认后基本不变） | `name_cn` / `name_en` / `un_locode` | 港口中英文名 + UN/LOCODE 标准编码 |
| | `country_code` / `city` | 所属国家/城市 |
| | `lat` / `lng` | 经纬度（距离计算基础） |
| | `port_type` | 海港 / 河港 / 内陆港 / 空港 |
| | `position_desc` | 港口定位（如"美西门户""北欧枢纽""中东转口中心"） |
| | `characteristics` | 特点（天然深水良港/人工港、可泊船型、锚地条件） |
| | `berth_depth_m` / `max_vessel_size` | 泊位水深、可接纳最大船型 |
| | `suitable_cargo` | 适用货类（集装箱/散杂货/液体散货/冷链…） |
| | `suitable_shipping_modes` | 适合发货方式（整箱FCL/拼箱LCL/散货Bulk/滚装RoRo/空运/海铁联运…） |
| | `connected_corridors` | 经济腹地/主要集疏运通道 |
| **动态运营数据**<br>（随市场变化，需定期更新） | `throughput_rank` / `congestion_level` | 吞吐量排名、拥堵程度 |
| | `major_carriers` | 主要挂靠船司 |
| | `avg_dwell_days` / `port_charges_level` | 平均滞港天数、港杂费水平 |
| | `last_verified_at` / `source` | 数据核实时间与来源 |

  地址→最近港口匹配：按经纬度球面距离排序 + `port_type`/`suitable_cargo` 过滤（如大件货排除空港），输出 Top 3 候选供业务选择。
  静态主档一次整理长期使用；动态运营数据标注 `last_verified_at`，超期提醒重新核实。

数据填充路线：手工录入 → 商情雷达品名词频沉淀（`source=intel_signal`）→ AI 批量提取（Phase 7）。

### 6.6 市场调研工位 `research`（已上线，2026-09-22）

### 6.7 官网爬取（地图源工位的产品信息通道）

**为什么必须爬官网**：Google Places 的字段全部是**店铺级**（名称/地址/电话/评分/
`primary_type`/`website`），**没有任何产品字段**。产品（图片、当地叫法、规格）
只能从官网 HTML 提取。

```
POST /api/v1/leads/{id}/crawl        单条爬取
POST /api/v1/leads/crawl-batch       批量（默认只爬 crawl_status='pending'，上限 20）
```

爬取管线（全部为**确定性脚本**，无 AI）：

```
GET website（js.fetch，浏览器 UA）
   ↓
去 <script>/<style> → 正则提取
   ├─ <meta property="og:image">       → product_image_url
   ├─ <h1> / <title>                   → product_name
   ├─ <meta name="description"> + 正文  → spec_raw（截断 1200 字符）
   └─ href 命中 /product|/catalog|…    → link_url
   ↓
规格结构化（脚本正则：尺寸/材质）
   ↓
crawl_status ← success | failed | no_website
```

**手动触发，不自动爬**：避免对目标站高频请求被封禁。

**CSV 导入**：地图源工位支持一次性导入完整业务表格（产品图片 URL、中文对照、
规格、国家、城市、店铺、店铺类型、电话、链接、官网、地址、能否提供），
无需逐条爬取。`能否提供` 列解析 `TRUE/FALSE/是/否/1/0`，**未知值一律落 NULL**。

### 6.8 情报体系数据回流闭环（第一版不接，接口预留）

## 8. 业务流程规划（后续细化）

以下为**方向性**业务流程，具体状态机、审批流、异常处理在工位开发时细化：

### 8.1 询盘录入 → 成交 → 订单/票据（核心链路）

```
收到询盘（邮件/WhatsApp/阿里/展会/其他渠道）
        │
        ▼ 录入询盘信息
客户管理工位
  ├─ 客户不存在 → 自动建档 + 首条询盘记录
  ├─ 客户已存在 → 关联客户，新增询盘记录
  │
  ▼ 匹配市场对照工位
┌──────────────────────────────────────┐
│ ① 地址 → market_ports 最近港口        │
│ ② 产品+地区 → 常见规格/品名对照       │
│ ③ 用途 → 适用产品类别                 │
└──────────────────────────────────────┘
  │
  ▼ 业务员跟进，更新询盘状态
询盘中 → 已报价（→ 智能报价工位生成报价单）
      → 已成交 ──► 自动生成订单（转入订单工位）
      → 已流失
  │
  ▼ 订单工位履约
发货 → 外贸票据工位自动生成 PI/CI/PL/B/L
```

各工位可**拆分开单独使用**（独立价值），组合后形成完整业务闭环。

### 8.2 进出口情报 → 报价工位
1. 商情雷达采集货运记录 / 买家询盘信号
2. 业务员在报价工位选取信号（引用 `intel_shipments`），触发报价单草稿
3. 报价工位结合 `product_skus` 定价，生成 `quote_orders` + `quote_order_items`
4. 写入 `quote_order_shipment_refs`，建立信号溯源
5. 报价单发送买家 → 确认/拒绝/过期

### 8.3 报价工位 → 订单工位
1. 买家确认报价单（状态 = accepted）
2. 业务员一键转化报价单 → 销售订单
3. 写入 `order_quote_refs`，复制行项到 `order_items`
4. 订单工位跟踪履约、收款、出运

### 8.4 订单工位 → 外贸票据工位
1. 订单进入履约阶段，触发票据生成
2. 根据订单行项生成 PI / CI / PL / B/L 等票据
3. 写入 `trade_doc_order_refs`，记录票据来源
4. 票据可下载/发送/归档

### 8.5 订单工位 → 进出口情报（回写）
1. 订单实际出运后，业务员录入出运信息
2. 写入 `intel_shipments`（商情雷达作为下游接收）
3. 写入 `order_shipment_refs`，完成物流闭环

## 10. 不变量 (Invariants)

> 新增工位时必须遵守，违反视为架构回归。

1. **表前缀**：`{domain}_*`，禁止无前缀表
2. **租户隔离**：所有表必含 `tenant_id`，查询必带租户过滤
3. **跨工位只读**：下游可读上游表，禁止跨工位写
4. **关联表幂等**：所有 `*_refs` 表必含 `UNIQUE(tenant_id, ...)`
5. **业务编码唯一**：`order_no` / `quote_no` / `doc_no` 等全局唯一，作为幂等键
6. **迁移单向**：生产库迁移只增不改历史表结构（允许新增列，禁止重命名/删除已有列）
7. **独立部署**：任何工位可单独部署/回滚，不影响其它工位
8. **订阅可见性**：未订阅工位的 API 返回 404（不暴露存在性），前端显示引导页
9. **订阅隔离**：未订阅工位的代码不执行、数据不写入、入口不渲染
10. **订阅防绕过**：跨工位写入前必须检查目标工位订阅状态
11. **脚本优先**：能确定性计算的（规格提取、去重、过滤、计数）用脚本，
    不用 AI。AI 只用于难量化环节，且必须有降级路径（模板/留空），禁止臆测写入
12. **人工判定优先**：商业判断字段（如 `can_supply`）由用户填写，三态存储
    （`TRUE`/`FALSE`/`NULL`），不设默认值，禁止 AI 推断
13. **改名不迁移**：展示层命名变更不改表名/URL/API 前缀，避免破坏性迁移
14. **绑定只在请求期读**：Worker 的 vars/secrets 在 import 期读一定是空值
    （`os.environ` 不可靠），必须走 `request.scope["env"]` / `_binding()`；
    **secret 一律不得保留公开默认值**（缺失则 503，宁可不服务）
15. **路由显式声明**：`/api/*` 与 `/health` 必须在 assets 的 `run_worker_first` 中声明，
    禁止依赖“资产未命中才落到 Worker”的隐式行为（否则健康检查会被 SPA 回退伪装成 200）
16. **默认闭合的鉴权**：新增端点必须带 `Depends(_get_current_user)`；
    公开端点仅限 `login` / `health`（`bootstrap-admin` 用一次性 token）；
    **actor/tenant 一律取自 token，绝不信任请求体**
17. **埋点不阻断业务**：事件上报失败必须静默吸收（不重试风暴），
    但写入权限受鉴权约束（未登录不上报）
